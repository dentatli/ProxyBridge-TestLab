## Что проверяем

В исходном опыте назначение и локальный relay были loopback. Все 96 отказов исходной очереди сопровождались отказом первого SYN/SO_PAUSE_ACCEPT, повтором и исходным STATUS_NOT_FOUND на принятом сокете. Очередь 1024 устранила отказы, а задержка приёма более 650 мс сама по себе их не вызвала.

Новый контроль меняет исходное назначение на отдельный сетевой узел. Он проверяет найденную зацепку о loopback Connect/Redirect, но не заменяет наблюдение внутреннего жизненного цикла записи Windows.

## Роли машин

Пользователь подтвердил 2026-10-07: Windows VM и Linux VM находятся на **одном физическом ПК**. Windows использует системный HTTP-прокси для работы Codex (снимок настроек, отдельный от тестового SOCKS5). Его настройки сохраняем. Опыт проверяет выход за loopback текущей Windows VM, но не независимость физических машин/ресурсов. Конфигурация виртуальных коммутаторов/NAT и возможный TUN на физическом хосте пока не проверены.

В закреплённом CTS `-conn:ConnectEx` выбирает Winsock `ctsConnectEx`; реализация передаёт заданный target sockaddr в `ctConnectEx`. Это путь raw TCP, не HTTP-запрос через системные HTTP proxy API: [Microsoft pinned ctsConnectEx.cpp](https://github.com/microsoft/ctsTraffic/blob/b0e2a48f30fb7caaaa9994ee2dea2a177a4639e2/ctsTraffic/ctsConnectEx.cpp). На уровне этого кода системный HTTP-прокси не используется. Однако это не исключает сетевой NAT/TUN/transparent interception вне процесса. Смену адресов наблюдаем по GUID-связанным журналам, её внутренний механизм не приписываем HTTP-прокси только по совпадению IP хоста.

| Машина | Роль |
| --- | --- |
| Текущий ПК | Тот же Windows, диагностические CLI/Core/driver, ctsTraffic-клиент, локальный SOCKS5, kernel/Core/исходный NTSTATUS/TCP-журнал |
| HLK-машина | Контролируемый ctsTraffic-получатель; журнал запуска, целостности, GUID соединений и завершения |

При выборе Linux VM роль HLK-машины заменяет Linux-получатель с доказанной совместимостью с закреплённым Windows ctsTraffic. Существующий Linux pb_net_endpoint обслуживает другой протокол и не заменяет ctsTrafficReceiver автоматически. В проекте уже есть SSH/server provisioning для Debian/Ubuntu/systemd; новый lab benchmark путь пока заблокирован REMOTE_CONTROLLER_PENDING. Выбор удалённого SOCKS5 в интерфейсе и выбор внешнего получателя — разные параметры топологии.

ProxyBridge на HLK-машине для этого контроля устанавливать или запускать не требуется. Назначение должно быть отдельным сетевым узлом, а не собственным LAN-адресом текущего ПК. Если это VM, важно зафиксировать, где находится её хост и как устроена сеть.

## Условия опыта

Два варианта: локальное назначение 127.0.0.1 и внешнее назначение на IPv4 HLK-машины. В обоих используется исходная очередь Core, та же версия Windows и одинаковые файлы продукта. Очередь 1024 не заменяет исходный вариант в этом опыте. Каждый вариант: ConnectEx, 32 ожидающих подключения, 4 → 64 → 256 → 640 → 4, удержание 8 с, 64 KiB/с на соединение, 512 KiB проверяемых данных на соединение, исходный single query и shutdown:rude. Восстановление проверяется на том же работающем CLI.

Максимальный заданный поток данных до получателя: 640 × 64 KiB/с = 40 MiB/с, около 336 Мбит/с без накладных расходов. Узкое место сети или приёмника фиксируется отдельно: оно может изменить нагрузку и не должно автоматически называться ошибкой ProxyBridge.

Порядок и топология сохраняются в отчёте. Один новый внешний прогон нельзя безусловно сравнить со старым локальным прогоном: различия времени и состояния системы должны быть явно указаны. Для контроля причинности предпочтительна новая парная серия с подтверждённым триггером в обоих вариантах.

## Реализация завершённой пары

Привязки реализованы отдельным opt-in `ExternalReceiverPair`: `Invoke-KernelTcpExternalReceiverDiagnostic.ps1`, общий диагностический dispatcher, `Invoke-LocalTcpConnections.ps1`, `ConnectionLoad.psm1`, строгая SOCKS allowlist и external evidence/report modules. Обычные локальные параметры остались прежними. Контракт связывает sealed private SSH-профиль, exact destination и бинарники; стандартный UI удалённого режима не включался.

Linux-получатель использует проверенный CTS push wire protocol и закреплённый receiver hash; каждую фазу обслуживает отдельная ограниченная systemd unit. Собраны start/stop/collection/exit и оригинальный JSONL. GUID, 512 KiB pattern/hash и результат связывают его с настоящим Windows CTS; равенство endpoint после трансляции не предполагается. Core использует исходную очередь, а SOCKS5 остаётся локальным Windows fixture с allowlist ровно выбранного IPv4/порта.

Контроль kernel/native/Core/TCP и NTSTATUS использует raw QPC внутри Windows; QPC Linux не сравнивается с ним. Фактический relay tuple взят из наблюдений, не из предположения о внешнем назначении. В полученной паре он оказался loopback в обоих вариантах.

## Критерии вывода

| Наблюдение | Допустимый вывод |
| --- | --- |
| В обоих вариантах подтверждены отказ первого SYN и повтор; NotFound только в локальном | Усиливается зависимость от исходного loopback-назначения; точный внутренний механизм ещё не установлен |
| При подтверждённом триггере NotFound есть и с внешним назначением | Исходное loopback-назначение не необходимо для отказа; общий loopback relay ещё не исключён, нужен жизненный цикл записи |
| Внешний вариант успешен, но отказ SYN и повтор не возникли | Триггер не воспроизведён; результат не различает гипотезы |
| Ошибка соединения/передачи на участке SOCKS5 → получатель | Отдельная сетевая/fixture-ошибка, не замена исходного verdict контекста |
| Не хватает журнала, есть потеря событий или неоднозначный match | INCOMPLETE; не PASS и не доказательство исправления |
