# Минимальный следующий опыт: сравнить поле при приёме и при запросе

USER просит минимизировать число точек и тормоза VM. Четыре гипотезы не требуют четырёх точек: одно наблюдение может разделить несколько вариантов, а проверка одной гипотезы о lifecycle может потребовать нескольких мест. Предварительный пятисобытийный кандидат из [результата bounded328](KERNEL_QUERY_BOUNDED_RESULT_2026-10-17.md) не включается целиком.

## Первый причинный вопрос и две активные точки-кандидата

Нужно различить: у принятого endpoint указатель на redirect record уже NULL на accept join либо он ненулевой там и NULL к исходному query Core. Привязка должна относиться к одному принятому соединению/времени жизни endpoint, а не только к повторяющемуся адресу.

| Кандидат | Место | Наблюдение |
| --- | --- | --- |
| A: ACCEPT_JOIN | tcpip!WfpAleAuthorizeAccept+cbe, RVA1568a | Endpoint, поле1c0 после общего участка retrieval/store, NBL и доступные признаки вызова |
| B: QUERY_READ | tcpip!WfpAleProcessSocketOption+2c4, RVA12157c | То же поле непосредственно перед исходным запросом Core; прежний ioctl filter980000dd |

Это **две активные точки всего**, а не две дополнительные к нынешним QUERY_READ/STATUS. QUERY_STATUS в таком новом профиле остаётся отключённой. Оригинальный результат API10022 продолжает сохранять Core; новый опыт не измеряет NTSTATUS на выходе независимо. Уже наблюдённые восемь NULL/C0000225 не означают автоматического NTSTATUS-подтверждения в следующем capture. Для другого сочетания record/API ошибки может понадобиться вернуть STATUS отдельным обоснованным профилем.

ACCEPT_JOIN — общий выход нескольких путей. Он показывает состояние поля в данном месте, но **не доказывает выполнение store или успешный retrieval**. Некоторые пути функции могут не дойти до join; отсутствие A не считается отсутствием записи. Этот capture не даёт полного CREATE/ATTACH/FREE покрытия.

## Как трактовать пару при проверенной идентичности

| Поле в A | Поле в B | Что можно исследовать дальше |
| --- | --- | --- |
| NULL | NULL | Указатель отсутствует уже на join; разбирать gate/retrieval/store раньше |
| Ненулевое | NULL | Между наблюдениями поле изменилось; искать clearing/замену/освобождение, не объявляя FREE доказанным |
| Ненулевое | Ненулевое | Проверить равенство указателей и Core/API результат; это не воспроизведение прежней NULL ветки |
| NULL | Ненулевое | Возможна более поздняя установка либо ошибка привязки; изучить границы наблюдения |

Без надёжной пары A/B вывод о переходе запрещён. В прошлой серии281 различных endpoint pointers приходились на296 query, stack scope повторялся. ExecutingPID не равен owner. Нельзя фильтровать только record!=NULL: это исключит именно искомые отказы.

## Число точек не равно стоимости

В сохранённой семиточечной четырёхсоединительной пробе184140 зарегистрированы25 ACCEPT_JOIN и4 QUERY_READ. Среди24 ACCEPT_RETRIEVE_RESULT двадцать не относятся к четырём исходным query; executing Core PID встречался и у таких событий. Поэтому замена STATUS на нефильтрованный общий ACCEPT_JOIN может **увеличить** число остановок/вывода, хотя активных точек останется две. Сравнение относится к тому capture, не является прогнозом следующего.

До stage нужно обосновать отбор целевого listener/соединения, пригодный и при NULL record, и достаточную идентичность A↔B. Только PID/ненулевой record не подходят как доказательство отбора. Фильтр в debugger action уменьшает вывод, но сам по себе не обещает отсутствия издержек от остальных hits. Окончательное сравнение вмешательства — только новой проверкой на четырёх соединениях, не по числу точек на бумаге.

В saved disk prologue WfpAleAuthorizeAccept r8w копируется в r13d и в локальный слот `[rbp-7c]`. **Сам r13 нельзя считать надёжным port filter на join:** на отдельных ветвях он переиспользуется под адрес диагностической строки (RVA14d61/150fd). Даже похожее на порт значение на обычном пути не доказывает его смысл на failed path. Исходный r8w в `[rbp-7c]` — только кандидат для дальнейшего разбора: сохранение видно в коде, но роль local/remote port и порядок байтов ещё не подтверждены для фильтра. Не превращать эту догадку в условие и не читать произвольные offsets endpoint. Сначала проследить данные/сохранённые символы и подготовить безопасную проверку значения, если статически его назначение не устанавливается.

## Стоп-пункт

Это выбор направления и неустанавливаемый план, не готовый stage/kit. Предпочтение — две активные точки для первого узкого вопроса, **при условии пригодного отбора и привязки**. Если это условие не обеспечивается, не обещать полноту и не запускать общий listener logger ради формального числа2.

Следующая работа — офлайн уточнение фильтра и flow binding, затем отдельный минимальный stage/kit и USER четырёхсоединительная проверка actions/стоимости. Не менять и не использовать старые frozen kits с новым профилем; не reload старого stage. Состояние существующих3/4 сначала уточняется перед любой будущей сменой: в последней console bd3/bd4/g без ошибок, но post-bd bl отсутствует. Новых Break/enable/Run агент не выполняет. Перед каждым будущим USER Break/enable — предупреждение о паузе всейVM/Codex/RDP, recovery на физическом ПК, команды по одной/g отдельно. Новый Run ещё не согласован конкретным готовым комплектом. Продукт не менять.
