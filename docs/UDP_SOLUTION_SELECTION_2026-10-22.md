# Выбор решения UDP при приоритете веса и скорости

USER: предложить несколько решений и выбрать эффективное при приоритетах
«вес и скорость». Здесь вес понимается как размер поставки и потребление
RAM/CPU, скорость — задержка и пропускная способность. Срок реализации
оценивается отдельно. Продукт пока не изменяется.

## Сравнение

Оценки архитектурные, не результаты benchmark.

| Вариант | Расходы при работе | Реализация | Решение |
| --- | --- | --- | --- |
| Исправить wildcard, добавить IPv6, сохранить общую map/association | Минимальные изменения | Быстрее остальных | Не решает потерю назначения и cross-delivery; не годится как полное исправление |
| ALE redirect на отдельный локальный порт каждого потока, полные SOCKS associations клиентов | Дополнительный relay socket/порт на поток; нет копирования payload в собственный device channel | Ближе к текущему пути, но нужны готовые порты или асинхронное ожидание bind до redirect | Возможный прототип; лимит портов, память sockets и создание потоков делают его менее привлекательным при масштабировании |
| WFP datagram capture + пакет с metadata через асинхронный device channel | Нет локального UDP relay socket на поток; есть копирование payload и очередь kernel/user | Больше работы в драйвере, включая receive injection и lifecycle | Выбран как основной вариант при приоритете веса и скорости |
| TUN + готовый tun2socks/userspace network stack | Дополнительный адаптер/компонент/стек, более широкий объём обработки | Быстро только при наличии подходящего готового компонента и решённых правил выбора приложений | Для текущей задачи избыточен |

Отдельный локальный порт на поток не объявляется неработоспособным: это
реальный альтернативный дизайн. Но он нуждается в проверке первого пакета,
повторного использования портов и обратного redirect для connected UDP.
Менять source port на ALE_CONNECT_REDIRECT для кодирования ID нельзя:
Microsoft поддерживает изменение local address/port только на bind redirect.
[Using Bind or Connect Redirection](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/using-bind-or-connect-redirection).

## Выбранная схема

1. TCP оставить на существующем пути. Для UDP использовать WFP datagram/
   transport interception вместо перенаправления всех пакетов в один relay.
   Отбор приложений и привязку к endpoint подготовить на подходящих ALE
   событиях; не рассчитывать на наличие PID на каждом datagram callback.
2. Передавать Core запись с payload, family, фактическими source/destination,
   endpoint/session ID и поколением. Сохранить compartment/interface/scope
   metadata, нужные для правильной обратной доставки. Драйвер держит
   минимальное состояние; SOCKS и правила остаются в Core.
3. Использовать ограниченную очередь и асинхронные pending IOCTL/read.
   Возвращать сразу доступные пакеты пачкой, не ждать таймер ради наполнения
   пачки. Это заменяет recvfrom + QUERY_UDP единым получением payload/metadata;
   но само по себе не доказывает уменьшение общих CPU/copy расходов.
4. SOCKS association выделять на исходный socket endpoint + generation +
   proxy config. Разные назначения одного клиента могут использовать одну
   association; association на каждый remote destination не нужна.
   Отдельные клиенты не объединять. ID endpoint надёжнее одного PID/порта.
5. Ответ определяется владельцем upstream UDP socket и адресом из SOCKS
   заголовка. Драйвер инжектирует его клиенту с адресом реального удалённого
   отправителя; общую эвристику last_activity удалить. IPv4/IPv6 используют
   один контракт. Обратную доставку connected и unconnected UDP проверить
   отдельно, не считать наличие injection API доказательством готовности.

WFP предоставляет асинхронную инъекцию transport/datagram данных для обеих
семей; корректные заголовки/checksums, lifetime NBL, completion и защита от
повторного перехвата остаются обязанностями реализации.
[Receive injection](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fwpsk/nf-fwpsk-fwpsinjecttransportreceiveasync0),
[send injection](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fwpsk/nf-fwpsk-fwpsinjecttransportsendasync0).

SOCKS association требует своего TCP control connection и UDP socket; это
основной неизбежный расход выбранной простой схемы разделения клиентов.
TCP живёт вместе с association, handshake выполняется при её создании,
а не на каждом пакете. Это следует учитывать и в задержке первого пакета,
и в лимитах SOCKS сервера. [RFC 1928, sections 6–7](https://www.rfc-editor.org/rfc/rfc1928.html).

## Ограничение расходов

- Один асинхронный event loop/IOCP для множества sessions; без потока на
  клиента и без блокирующего SOCKS handshake в общем relay loop.
- Переиспользуемые буферы, ограниченные очереди и учёт потерь при переполнении.
  Не выделять автоматически нынешние 256 KiB socket buffers каждому клиенту;
  размеры выбрать по измерениям целевой нагрузки.
- Кэшировать решение правил в пределах актуальной версии конфигурации,
  сохраняя раздельные правила разных назначений. Не вычислять имя процесса
  и не перечислять процессы на каждый пакет.
- Удалять состояние по lifecycle endpoint, очищать при завершении owner
  session; generation защищает от повторного использования идентификаторов.
- Первую версию сделать на штатном асинхронном I/O. Shared memory/ring и
  более сложные схемы объединения associations отложить до профилирования.

## Как подтвердить выбор

Сначала минимальный вертикальный прототип: один IPv4 datagram с metadata →
Core → explicit SOCKS → receive injection, затем connected/wildcard и IPv6.
После функциональных gates — два назначения одного сокета, два клиента
одного назначения, повторное использование endpoint и остановка owner.
Использовать отдельные свежие диагностические опыты, не возобновлять captures;
не добавлять запрещённые product tests.

Измерить отдельно размер поставки, private bytes/Core, kernel nonpaged memory,
число handles/sockets, CPU, packets/s, потери и p50/p95/p99 задержки — включая
первую association и установившийся обмен. На малом и большом числе клиентов,
малых и крупных payload. До этого нельзя обещать конкретные проценты ускорения,
объём RAM или превосходство над вариантом с портами на любой нагрузке.

Итоговый выбор: собственный ограниченный UDP datagram path в имеющемся WFP
драйвере + association на endpoint/config в Core. Это инженерный выбор по
структуре расходов и корректности; не самый короткий патч по сроку разработки.
Исходная [причина](UDP_FLOW_IDENTITY_ROOT_CAUSE_2026-10-22.md) остаётся baseline.
