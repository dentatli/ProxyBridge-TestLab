## Что проверено в кадре точки 17

В сохранённом live code log 17:31 пролог содержит `push r12`, `push r14`, `push r15`, `sub rsp,40h`. На +0x155 выполняется `mov rbx,[rsp+60h]`; `add rsp,40h` расположен позже, на +0x169. Следовательно, для обычного входа в эту функцию body RSP = entry RSP − 0x58. Обращения `body RSP+0x80` и `body RSP+0xa0` соответствуют `entry RSP+0x28` и `entry RSP+0x48`. Сам код читает эти slots на других участках функции.

15 выбранных инструкций пролога/чтений/восстановления совпали побайтно между прежним live log и закреплённым PE `fwpkclnt.sys` SHA256 `e846c63a88a153ee7785a68a1cc0a73dea598736c5cc4490cce95abf3e7d1143`. PE runtime function 0x4a60..0x4ed7 и UNWIND_INFO по RVA 0x471c8 независимо дают три PUSH_NONVOL по 8 bytes и ALLOC_SMALL 64 bytes: суммарно 0x58. Формулы unwind соответствуют [описанию Microsoft](https://learn.microsoft.com/en-us/cpp/build/exception-handling-x64). Это проверка выбранного сохранённого кода, не всего нынешнего live image.

Таким образом, гипотеза «на +0x155 RSP уже восстановлен, поэтому +0x80/+0xa0 ошибочны» не подтверждается этим кодом. Однако аварийный log не содержит RSP, stack bounds, raw slots, вызывающего стека или сведений о доступности страниц в момент ошибки. Он не доказывает, какое из двух чтений отказало и почему. Нельзя объявить ошибку смещения, повреждение стека, transport loss или причину сброса TCP установленными. Менять смещения наугад или включать 17 для повторения ошибки не требуется.

Условие использует bitwise `and`, а не защиту с коротким замыканием; [MASM](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/masm-numbers-and-operators) определяет `poi` как чтение памяти. Наличие gc в обеих ветках не защищает от ошибки вычисления самого условия: в данном log после error отладчик оставался на приглашении. [gc](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/gc--go-from-conditional-breakpoint-) возобновляет исполнение только когда команда до него дошла.

## Как связывать запись с конкретным исходным запросом

Для каждого соединения строить цепочку: native GUID/tuple/PID → CTXDIAG seq/socket/relay_pid/thread и CTXTIMING → QUERY_READ/STATUS одного KD thread/scope/endpoint → ACCEPT_RESULT/STORE этого endpoint → record поколения CREATE_POST → FREE_ENTER/RETURN. KD PID/TID печатаются в hex, Core — decimal; нормализовать значения. Thread pointer связывать с PID/TID только в подтверждённой жизни thread. PID исполнения в DPC/packet пути не считать владельцем соединения.

Одна KD query-пара должна однозначно соответствовать единственному исходному Core query на том же PID/TID в этом опыте. При нескольких query одного thread, дубликатах, пропусках или смене потока связь остаётся неоднозначной. Количество четыре, порядок строк и ближайшее время не заменяют доказательство. В старых телах KD нет общего с Core rawQPC; абсолютную временную связь эти точки не устанавливают. Context/record/address A/B без проверенного преобразования не равны native tuple. Повторное использование record/endpoint требует границ жизни.

NBL attachment пока остаётся отдельным пробелом. После работоспособного four logger выбрать узкие caller sites в уже исследованных `tcpip!FastLoopback`/send-cold paths непосредственно до/после association key5, с отдельной проверкой кода/аргументов; не возвращать все generic fwpkclnt точки. Сопоставить NBL/record с accept result/store по явным переходам. Новые bp сейчас не предлагаются к установке. Полную нагрузку решать только после baseline review; успешный baseline не доказывает механизм отказа под давлением очереди.

Для исходного сбоя различать: retrieval key5 вернул C0000225; retrieval успешен, но endpoint получил другую/NULL запись; запись исчезла между store и query; query идёт по другому endpoint. Чтобы доказать конкретный механизм, нужен соответствующий переход и владелец/жизнь объектов у отказавшего соединения плюс успешное сравнение. Контроль backlog1024 и backlog1024+650ms подтверждает роль условий очереди, но не выбирает одну из этих причин.
