# Предложение: отдельно оценивать передачу данных и закрытие TCP

Статус: предложение на выбор пользователя, 2026-10-02. Обычная методика ещё не изменена. Пользователь выбрал сначала выяснить причину и влияние исправления на сопоставимость скорости. Переход обычных benchmark на rude не согласован.

В выбранной 4.0.0 два upload с обычным закрытием завершились сбросом. Подробный журнал последнего подтвердил: 64 MiB переданы, клиент проверил ответ завершения, успешно вызвал `shutdown(SD_SEND)`, затем получил `WSARecv 10054` в ожидании ответного FIN. Отдельный upload со штатным `ctsTraffic -shutdown:rude` прошёл проверку данных и завершился без ошибок. Источник RST пока не установлен; ядро ProxyBridge не исправлялось.

Предлагаемый результат для пользователя:

| Проверка | Что показываем при текущем дефекте |
|---|---|
| Передача данных | Проверены объём и содержимое, общий ConnectionId, фактический маршрут и контролируемый получатель |
| Обычное закрытие TCP | Ошибка: сброс после передачи данных; этот результат остаётся FAIL |
| Скорость передачи | Отдельный ограниченный benchmark при одинаковом режиме закрытия у обеих версий и прямой базы |

Для benchmark использовать готовый режим ctsTraffic `-shutdown:rude`: он завершает соединение после проверки ответа DONE, без ожидания обычного ответного закрытия. Настройка одинакова для OFF, ProxyBridge 4.0.0 и Driver; никакого исправления Core/driver или игнорирования ошибок данных. Проверки native exit/Succeeded, verify:data, объёма/GUID, PID/маршрута/SOCKS-потока, CPU/RAM и штатной остановки выбранных ресурсов остаются обязательными.

Проверка обычного закрытия запускается отдельно. После новой версии она проводится снова: при подтверждённом успехе результат этой проверки меняется на PASS. Benchmark не может сам объявить дефект исправленным. В общем итоге известная ошибка корректности остаётся видимой, даже если скорость удалось измерить.

Первый шаг после выбора этой методики — подготовить свежую проверку upload/download 4.0.0, OFF/PROXY, 4 × 64 MiB при настройке 8 MiB/s. Это проверка готовности; запрос сведений о сокетах во время переноса ограничивает интерпретацию скорости. Затем отдельно подготовить повторяемую методику сравнения версий с одинаковыми условиями наблюдения. Результаты прежних graceful и isolated diagnostics не объединять с новой серией; между версиями нужна перезагрузка.

Ограничения: benchmark передачи исключает ожидание обычного закрытия; заданный темп не показывает максимальную ёмкость. Этот выбор не означает корректность всех TCP-сценариев, успешный download или готовность сравнения версий — их ещё необходимо подтвердить.

Альтернатива: сначала установить источник RST дополнительной диагностикой. Это отдельная работа; текущие журналы установили этап отказа, но не компонент, сформировавший сброс.

Дополнительная проверка исходника неизменного SOCKS backend лаборатории выявила закрытие целого socket после EOF вместо явного сохранения обратного направления. Его роль в сбросе не установлена. Перед атрибуцией дефекта ProxyBridge обоснован контроль самого SOCKS backend без ProxyBridge; выбранный режим benchmark пока не менять.

Контроль без ProxyBridge подтвердил потерю ответа после EOF в original SOCKS fixture и её устранение отдельным EOF-only вариантом. Ответ до EOF проходит и в original. Поэтому связь этого ограничения с ctsTraffic reset4.0.0 ещё нужно проверить; текущий следующий запуск — isolated graceful upload с diagnostic half-close fixture. Скорость исправленного стенда пока не измерена.
