## Что означают непонятные числа

**Проверенных обменов.** Это число успешно проверенных логических транзакций адаптера, а не фиксированное обязательное количество и не пропускная способность. Для большинства application cases время30s,4потока и ограничение100transactions/s на поток. У3размеров сообщения ориентир4×100×30×3=36000. В HTTP/2 sweep WinDivert35940, WFP35964:24обмена/0.0668%, обе проверки PASS. Граница временного окна, пачки и планирование допускают небольшие отличия; сами по себе они не доказывают превосходство. Другие успешные примеры: HTTPS35960vs36000, gRPC11988vs12000, POP311952vs12000. Семантика транзакции зависит от протокола; сравнивать только один и тот же case/profile.

SFTP WFP6184/WinDivert5005 — более заметная разница (+23.56% к WinDivert), но обе стороны ниже ориентира12000. PASS подтверждает выполненные корректные обмены, а не достижение заданного темпа. Это наблюдаемая производительность данного client+proxy+origin пути; предел самого ProxyBridge не установлен. Требуются отдельные target/actual rates и нагрузочная достоверность, не ranking по одному счётчику. HTTP3 WFP12000/WinDivert3000 — иной случай: у WinDivert3из4flows завершились ошибкой. Это не доказательство четырёхкратной разницы скорости. HTTP3 sweep у WinDivert остановился после первого размера (2985обменов); его итоги нельзя сравнивать с3полными размерами WFP36000.

**Изменение памяти −0.25MiB.** Текущая формула last−first внутри окна измерения. WFP three-modes: private commit2.644531→2.398438MiB, delta−0.246094MiB. Это уменьшение занятой памяти, не отрицательный объём памяти. У WinDivert delta+0.0703125MiB. Сравнение двух изменений даёт−0.316406MiB/−450%, но относительный процент от малого изменения со сменой знака не сообщает полезной эффективности. Подсветка «меньше=лучше» для signed memory delta методически неверна: на результат влияют освобождение старых буферов/кэши/предыдущие cases одной retained Core session. Из этих endpoint differences утечка не следует. Нужны подпись «память после−до», сами before/after значения; без процента и winner для net change.

**Большие ресурсы WFP при tcp-connections.** Счётчики прочитаны без unavailable samples: WFP peak commit45.007812MiB, RAM44.6MiB,269threads/997handles; WinDivert3.855469MiB/7.51MiB/11threads/379handles. Case действительно доходил до128 удерживаемых TCP-соединений плюс echo probe, origin peak129 у обеих сторон. Это реальные наблюдаемые process peaks в этом окне. У WFP commit2.570312→2.167969MiB, threads13→7 и handles94→80 после нагрузки: пики не являются оставшейся навсегда памятью/потоками. Причина внутренней организации продукта здесь не исследовалась. CPU — mean всего case, память/threads/handles — peaks; они не обязаны относиться к одному моменту или одному шагу128. Нужна привязка ресурсов к фазе/числу соединений.

**Завершено/предложено TCP.** Для flow-rate: WinDivert969попыток/969полных успешных сеансов, WFP1136/1136. Это не фиксированное количество «предложенных» запросов: два workers в течение30s последовательно создают session, выполняют echo около50ms и закрывают. Реальный CPS31.84vs37.52 относится только к этому профилю; теоретический потолок от самого50ms×2workers порядка40/s без setup overhead. Максимальную способность создавать TCP-соединения тест не измеряет. Понятное представление: «успешных сеансов/попыток», «ошибочных сеансов», «сеансов/s», число parallel workers и профиль.

**RTTp99 в flow-rate.** Здесь это смешение baseline/recovery echo, а не RTT во время churn. Проверено histogram count: WFP baseline97210/recovery91717/churn0, WinDivert33804/33087/churn0. Для churn отдельно собраны1136/969 setup samples. Setup включает TCP+подписанную подготовку получателя, не только TCP handshake. Значения setup p99 WFP3.10ms/WinDivert17.52ms сравнимы в этом профиле. Общий RTTp99 без указания «до/после нагрузки» вводит в заблуждение. Нужны отдельные именованные интервалы, не общий RTT для этого case.

## Ошибки и пределы вывода

**WFP udp-connections.**8/32flows без потерь;128flows worker363557sent/360559confirmed, потеря2998/0.8246%, каждый flow0.774–0.881% (ни один не превысил1%). Invalid/send errors отсутствуют, все worker flows complete.128flow fingerprints совпали. Signed proxy udp_sent=udp_received=origin_received=360559, origin reply errors0. Не сошёлся только строгий100%учёт отправленных пакетов в proxy:363557vs360559. Поэтому route gate=false и общий report получает TRANSPORT_INCOMPLETE/ROUTE_UNVERIFIED, несмотря на допустимую по1%политику потерю. Это не доказанный дефект драйвера и не timeout ассоциаций. Наблюдаем потерю до учтённого forwarding relay; какая часть client/driver/OS/relay ответственна, эти данные не устанавливают. Лаборатория должна отдельно показывать packet loss, подтверждённый маршрут принятых потоков и недостаточную полноту отправочного учёта; не смешивать их в безусловное утверждение о неисправном транспорте. Guard не ослаблять и missing packets не превращать в PASS. Capacity control не был вызван: его нынешний trigger требует flow loss>1%, здесь его нет.

**WinDivert11FAIL.** UDP connected/unconnected/sweep/connections, HTTP3single+sweep, QUICsingle+multiplex, DNSUDP, mixed, stability. В обычном UDP примерно75%ответов не проходят flow-id проверку: пример11312sent/2828confirmed и8484FLOW_MISMATCH. В8flows baseline/recovery по1flow PASS, нагрузочный8flows —19778FLOW_MISMATCH. QUIC/HTTP3 у3из4flows handshake/connection terminated; DNSUDP0confirmed, response invalid/timeout. Это несовпадение идентичности/обмена, не просто медленная работа или ошибка процентов. Нельзя ранжировать latency/CPU/обмены этих FAILED cases как успешную производительность. Корневая причина продукта здесь не диагностировалась.

WinDivert stability выполнил только первый из8нагрузочных интервалов (7пропущены), WFP — все8. UDP sweep6vs1окон, HTTP3 sweep3vs1. Поэтому общее время и средние/пики по таким неполным cases не равнозначны. Полные runs45m06.8s vs36m54.6s не означают, что WinDivert быстрее заканчивает ту же работу.

## Что уже можно сравнить

Функциональные исходы и33успешные одинаковые пары — да, с точным смыслом каждой метрики. В текущем стенде WFP TCPupload≈1505.69MiB/s против239.41, download1491.90vs163.50. Но весь PC в WFP speed windows≈99.9%CPU: worker+origin используют основную долю CPU (например upload22.95%+52.52%ПК), поэтому потолок собственного transport ProxyBridge не отделён от предела генератора/приёмника/relay на том же host. Это измеренные локальные скорости, не максимум драйвера или реальной внешней сети.

CPU процесса клиента не является CPU всего драйвера; kernel work/memory WFP полностью не атрибутированы. Меньше client CPU не означает меньше PC CPU. При unbounded throughput/echo более быстрый вариант выполняет больше работы. Даже baseline echo не имеет общего фиксированного темпа: WFP≈1.72MiB/s против0.55 у WinDivert. Следовательно «зелёный меньший CPU» без равной фактической нагрузки/полезной работы не устанавливает эффективность. Простое time weighting здесь не причина странностей: tcp-connections samplemean/timeweighted WFP4.9281/4.9278%, WinDivert15.9366/15.9324%.

Один полный A/B не даёт вариативность/повторяемость; малые проценты не следует трактовать как устойчивый выигрыш. Это управляемые loopback scenarios, не доказательство корректности всего возможного трафика ПК.

## Необходимые следующие изменения лаборатории

1. Понятные определения/единицы/интервалы: attempts/completed/failures, before/after memory, phase-specific RTT; net memory без winner/percent.
2. Actual/target rate и выполненная доля окон у каждого application/load case; fail/partial никогда не сравнивать как полноценный benchmark.
3. Ресурсы по одинаковым нагрузочным фазам, отдельно от baseline/recovery; процессные peaks не выдавать за kernel footprint. Для расхода — равная достигнутая нагрузка/CPU cost per verified work, для максимума — отдельный headroom gate стенда.
4. Разделить loss policy и route accounting completeness, отражать uncertainty без снятия доказательных guards.
5. Повторы только выбранных репрезентативных профилей при необходимости оценки performance; новые полные runs без исправления смысла метрик не устранят эти ограничения.
