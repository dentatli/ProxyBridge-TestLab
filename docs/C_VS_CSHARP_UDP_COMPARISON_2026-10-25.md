# Небольшое сравнение обработчиков UDP на C и C#

Проведено 25 октября 2026 по запросу пользователя. Сравнивается конкретный небольшой транспортный прототип, не полный движок 51 сценария и не производительность ProxyBridge. Продукт/драйвер не запускались, лаборатория оставалась idle. Установленная preview44 и системные настройки не менялись.

## Одинаковые условия

- Windows10.0.26200,6 доступных логических CPU, CPUID Intel Core i5-14600KF, RAM около 9,76GiB. Это окружение агентской VM, не аттестация физического SUT.
- C: Visual Studio18 / MSVC,x64,/O2,/MT,/W4/WX. C#:NET10 Release,x64,framework-dependent, установленный runtime10.0.12, SDK10.0.401. Оба получателя — отдельный процесс с одним выделенным блокирующим UDP-потоком и общим 4MiB socket receive/send buffer. Никакой индивидуальной настройки priority/affinity/power.
- Общий нативный C-генератор:32/128 настоящих UDP-сокетов, одинаковая подача нагрузки обоим.512 байт детерминированных данных; пакет 576 байт с flow/sequence/QPC/run nonce/HMAC-SHA256. Каждый ответ проверен по source/flow/sequence/nonce/payload/HMAC, дубликаты учитываются. Python только управляет процессами и снимает ресурсы.
- C переиспользует Windows CNG HMAC object, C# — HMACSHA256/Span/SocketAddress. Прикладные буферы переиспользуются в обоих. Это сравнение реализаций/API/toolchain, не изолированной стоимости языка.
-3200/12800/64000 запросов/сек,4 сек измерения,3 повтора на каждый вариант с чередованием порядка. Каждый процесс предварительно прогрет 2 сек при 4000pps. Независимый Python probe проверил корректный ответ и отказ на 4 видах неверного пакета:MAC,payload при валидной MAC,nonce,длина.
- Из-за нестабильности первых коротких CPU-time измерений выполнен дополнительный контроль 12 800/64 000 pps на тех же бинарниках:4 сек прогрева,3 повтора,QueryProcessCycleTime. Оба измерительных набора вместе около 3,5 минут, не длинный suite, разделённый ради обхода лимита. Все целевые offered rates достигнуты; в одном основном C# измерении генератор не успел отправить 9 из 256000 запланированных, это не потери получателя.

## Результат

Медианы трёх повторов.12 800/64 000 pps — дополнительный контроль с 4 сек прогрева;3200pps — основной набор. RTT включает генератор и OS scheduling, не является чистым временем обработки сервера.

|3200pps,32flows|C|0|0,1212|не снимались|0,961|5,504|
|3200pps,32flows|C#|0|0,1216|не снимались|7,453|27,754|

|64 000 pps,128flows|C#|0|0,1411|30122|7,543|27,816|

Все 30 измерений двух наборов:0 потерь,0invalid,0duplicates,0senderrors. Это около 1,88 млн подтверждённых измерительных запросов на каждую реализацию, без учёта прогрева. Контрольные повреждённые пакеты отвергнуты обоими. Процессы завершены штатно.

На 12800pps диапазон p99 C0,1013–0,1070 мс,C#0,1066–0,1148 мс. На 64 000 pps:C0,1146–0,1464 мс,C#0,1324–0,1630 мс. Диапазоны пересекаются; устойчивого победителя по задержке из малого опыта нет. Основной набор также менял относительный порядок в зависимости от повтора.

CPU-time особенно шумит на малой нагрузке: первые короткие измерения давали от 0 до 53,9%одного ядра. Поэтому на них не строится вывод о превосходстве языка. В дополнительном наборе при 64 000 pps медианы 51,17%одного ядра у C и 55,47%у C# (8,53%/9,24%всего 6-CPU узла); диапазоны 46,87–52,73 и 51,95–59,37 соответственно. Process cycles на запрос у C ниже примерно на 7,9%при 12800pps и 6,9%при 64 000 pps. Cycle counters зависят от процессора/виртуализации/частот и не переводятся здесь в CPU-время.

Private commit — обязательства памяти процесса, working set — его резидентные страницы, включая разделяемый код. Сумма working set нескольких NET процессов не равна уникально занятой ими памяти всегоПК. Сравнение file size framework-dependentC#apphost с самостоятельным Cexe намеренно не проводится: NET runtime уже присутствует, его нельзя игнорировать при расчёте поставки.

## Что это даёт для выбора

1. Оба небольших компилируемых обработчика выдержали 128flows при 12800pps и 64 000 pps. Ограничение прежнего Python-стенда не является неизбежным пределом этих профилей.
2. C экономичнее в этом опыте: существенно меньше процессная память и умеренно меньше cycles/request. Разница не означает такого же множителя в полном HTTP/QUIC/SSH движке.
3. C# показал достаточную производительность для проверенного UDP профиля. Язык сам по себе не определяет честность сравнения: нужны одинаковые обработчики, свежие контрольные evidence и подтверждённая ёмкость стенда.
4. Для минимальных накладных расходов транспорта результат склоняет к C. Выбор реализации всех прикладных протоколов требует учёта корректности библиотек/жизненного цикла и отдельного измерения. Сложные протоколы должны оставаться настоящими, а не заменяться UDP echo.

Не измерялись максимальная пропускная способность, длительная стабильность, IOCP/multiworker варианты, SOCKS5/TCP/TLS/HTTP/SSH/QUIC или реальные WFP/WinDivert прогоны. Здесь один echo-получатель; полного пути генератор → SOCKS5 → origin нет. Новый генератор равномерно распределяет отправки между сокетами, тогда как прежние Python-потоки могли формировать всплески. Максимальный текущий HIGH-профиль 640 потоков × 1000 pps = 640 000 pps не проверялся. Результат 64 000 pps нельзя распространять на него. Пакет с 512 байтами данных отличается от прежнего JSON-формата лаборатории, поэтому цифры не являются прямым A/B старого полного движка.
