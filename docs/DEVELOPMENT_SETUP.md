Подготовлено на этом Windows-ПК 2026-09-28:

- .NET SDK 10.0.401 установлен через официальный пакет Microsoft.DotNet.SDK.10 в winget.
- Использованы существующие Visual Studio Community 2026 и MSVC x64 14.51.36231.
- Python 3.11.9 x64 установлен через Python.Python.3.11 в winget. Эта ветка нужна для сохранённого wheelhouse с `cffi cp311`.

## Идентичность файлов продукта

Перед действиями с продуктом реальный runner сохраняет `product-build.json`: SHA-256 CLI, лежащей рядом `ProxyBridgeCore.dll`, драйвера и настроенного GUI, общий отпечаток комплекта, размеры и доступные версии из ресурсов файлов. GUI и CLI должны находиться в одном каталоге, чтобы подготовка не запускала ядро из другой установки. Отсутствующий файл или несовпадение с ожидаемым хешем останавливает прогон до подготовки процессов/службы. UI автоматически добавляет хеш ядра в приватное окружение; при ручном использовании runner теперь также нужен `PB_EXPECTED_PROXYBRIDGE_CORE_SHA256`.

`Get-ProductBuildIdentity` из `modules/ProductBuild.psm1` выполняет только чтение файлов. Для `-Contract v4.0.0` он учитывает соседние `WinDivert.dll` и `WinDivert64.sys` с ожидаемыми `PB_EXPECTED_WINDIVERT_DLL_SHA256` и `PB_EXPECTED_WINDIVERT_DRIVER_SHA256`. Это доступно отдельно от runner, который всё ещё запрещает реальный запуск старой версии. Без ожидаемого хеша файл можно наблюдать, но статус `FILES_VERIFIED` не выставляется.

Необязательный `PB_PROXYBRIDGE_SOURCE_COMMIT` — заявленный полный SHA исходников, а не доказательство происхождения сборки. Версии из файлов могут отсутствовать. Совпадение хешей не подтверждает выбранный контракт, коммит, фактически загруженный драйвер или маршрут. Эти признаки в отчёте явно остаются неподтверждёнными. Технические хеши и заявленный SHA доступны в audit-export; приватные пути и секреты редактируются штатным фильтром.

Оба закреплённых CLI печатают `ProxyBridge is running. Press Ctrl+C to stop.` после успешного `g_Start` и регистрации обработчика управления. Это стандартный признак готовности для обеих версий; у Driver сохраняется возможность явно задать другой regex. Выживание процесса в течение stable_ms больше не является стандартным признаком запуска продукта. Сообщение не доказывает маршрут. Исходники: [v4.0.0](https://github.com/InterceptSuite/ProxyBridge/blob/22e53445e44481fad0f63c2a088aa91c0deda3af/Windows/cli/main.c), [Driver](https://github.com/InterceptSuite/ProxyBridge/blob/63be0ebf9bec92bfba95ef3d6729c375aa9af84e/Windows/cli/main.c).

`pb_console_host.exe --terminal` запускает собственный CLI в ConPTY и Windows Job Object. Процесс получает терминальные стандартные handles: его CRT не использует перенаправленный pipe stdout, который мог задерживать startup-сообщение. Вывод UTF-8/VT непрерывно передаётся отдельным потоком; чтение C# не ожидает завершения строки. STOP или EOF управляющего stdin передаёт байт ETX (Ctrl+C) в собственную псевдоконсоль. Оба CLI обрабатывают Ctrl+C. Закрытие ConPTY и дренирование ограничены по времени; ошибка или таймаут не дают успешную очистку. Схема — [документация Microsoft](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session) и [образец MiniTerm](https://github.com/microsoft/terminal/blob/main/samples/ConPTY/MiniTerm/MiniTerm/Terminal.cs); дополнительный runtime не нужен.

Старый режим отдельных pipes сохранён в помощнике: отдельная скрытая консоль, проверка её участников, `CTRL_BREAK_EVENT`. Планы CLI теперь выбирают терминальный режим для обеих версий. При ошибке или истечении времени завершается собственная job; смерть помощника также закрывает job. PID и проверяемый путь в runner относятся к продукту, а не помощнику.

`graceful_stop` означает передачу команды управления в транспорт, завершение процесса и его код 0; это не доказательство выполнения callback, окончания внутреннего `g_Stop` или очистки драйвера. `stop_transport` различает `conpty-ctrl-c-written-process-exited`, CTRL+BREAK, самостоятельный выход, принудительное завершение и ошибку. Проблема контролируемой остановки даёт `CONTAMINATED` и прекращает последующие сценарии независимо от разрешения продолжать другие ошибки.

ConPTY объединяет stdout/stderr продукта в терминальные кадры. `output_format=terminal-vt-merged`; содержимое сохраняется без изменения. Служебный stderr помощника остаётся отдельным. VT-коды удаляются отдельно для поиска startup-сообщения. Для восстановления наблюдаемых строк подключён готовый [pyte 0.8.2](https://pypi.org/project/pyte/) (Python 3.8+, LGPLv3, универсальный wheel) с wcwidth 0.2.13 (MIT). Это восстановление изображения терминала, а не доказательство полноты исходного журнала: одинаковые строки объединяются, порядок событий не гарантируется. `source_event_stream_complete=false`, `source_event_order_preserved=false` и `channel_capture_completed=false` сохраняются даже при успешном декодировании. Реальный legacy-режим и разрешение переключения версий остаются закрыты.

`src/pb_terminal_decode.py` использует геометрию помощника 240×80 и ограничения 8 MiB входа/10000 наблюдаемых строк. Runner вызывает его через ProcessAdapter, проверяет завершение, версии и хеш входа, затем разбирает только наблюдаемые маршрутные записи. Официальные префиксы CLI `[CONN]`/`[LOG]` удаляются перед разбором полезной части; исходная строка сохраняется в записи. Обезличенный `proxybridge-terminal-decode.json` разрешён для audit-export, приватный исходный `proxybridge-terminal-output.txt` не включён в этот список.

Библиотеки лежат отдельно в `bin/terminal-decoder/packages`, лицензии сохранены. Wheels сверены с SHA-256 официального PyPI; версии и хеши закреплены в `config/terminal-decoder-requirements.txt`. Для повторной подготовки имеется `scripts/Prepare-TerminalDecoder.ps1` (Python с pip; по умолчанию dev-venv). Скрипт скачивает только wheels с проверкой хешей и устанавливает их в отдельный каталог, не меняя пакеты dev-venv. В этом шаге wheels подготовлены напрямую; сам скрипт не запускался. Упаковщик копирует библиотеки и требует их лицензии; release-пакет не собирался.

Проверено 2026-09-30: синтаксис четырёх изменённых PS-файлов в PowerShell 5.1/7.6; Python py_compile; сборка UI — 0 ошибок/предупреждений. Ручной вывод штатного Windows PowerShell `[Environment]::OSVersion.VersionString` через ConPTY восстановлен как `Microsoft Windows NT 10.0.26200.0`; helper exit 0. Прямой декодер и вызов через PowerShell-адаптер вернули `DECODED_OBSERVATIONS`, полнота осталась false. Первая попытка выявила обращение к ещё не инициализированному экрану pyte; исправлено и проверено на том же реальном выводе. Автотестов, запуска ProxyBridge/драйверов/трафика не было. Маршрутные строки настоящего продукта и Ctrl+C пока не проверены.

Проверено 2026-09-30: помощник собран MSVC x64 `/W4 /WX`; синтаксис трёх PS-файлов и встроенный C# — PS 5.1/7.6. Попытка `cmd /c ver` с универсальной CRT-упаковкой аргументов дала ошибку команды; для ручного просмотра использована PowerShell. ## Наблюдение состояния перехвата

`modules/InterceptionState.psm1` подключён к реальному runner: `interception-before.json` создаётся до подготовки продукта, `interception-after.json` — после попытки сценария с runtime. Оба включены в audit-export. Автоматического запуска наблюдения при импорте модуля, DryRun или mock нет; самостоятельный вызов `Get-InterceptionStateSnapshot` требует `-AllowProductRuntime`.

Состояние и конфигурация WFP-службы наблюдаются через Windows SCM: соответствие её пути `PB_DRIVER_PATH` и хеша файла ожидаемому. Ранее применявшаяся `Win32_SystemDriver` не увидела свежую регистрацию на этой машине. Несовпадение, недоступность сведений или переходное состояние блокируют подготовку; после сценария они останавливают дальнейший прогон. Наблюдатель ничего не устанавливает и не меняет в службах. Сведения о файле на диске не подтверждают идентичность кода, уже загруженного в ядро.

Для WinDivert повторно используется официальный [windivertctl v2.2.2](https://github.com/basil00/WinDivert/blob/v2.2.2/examples/windivertctl/windivertctl.c). В приватном окружении одновременно задаются `PB_WINDIVERT_CTL_EXE`, `PB_EXPECTED_WINDIVERT_CTL_SHA256` и `PB_EXPECTED_WINDIVERT_OBSERVER_DLL_SHA256`. DLL должна лежать рядом с утилитой. Это необязательное подключение для обычного Driver-прогона; без него отчёт показывает `NOT_CONFIGURED`, а не отсутствие handles. Утилита отдельно не скачивалась, не поставляется в пакете TestLab и пока не запускалась. При её будущей поставке необходимо сохранить лицензионные файлы upstream (LGPLv3/GPLv2 dual license, см. заголовок исходника).

Наблюдатель фиксированно запускает `list` (REFLECT/NO_INSTALL), удерживая проверенные EXE и DLL от замены до завершения. Нет пользовательских фильтров и вызовов watch/kill/uninstall. Таймаут, ненулевой код, stderr, неполный сбор или неизвестный формат означают неопределённый результат и блокировку, когда наблюдатель настроен. Подтверждённый пустой вывод означает только `NO_HANDLES_OBSERVED` для совместимого с этой DLL семейства драйвера в момент снимка. Любые найденные handles мешают продолжению текущего контролируемого Driver-прогона; они не завершаются автоматически. В отчёт попадают PID, слой, флаги и приоритет, без путей чужих процессов и содержимого сетевых фильтров.

`pb_wfp_state.exe` дополнительно читает известные provider/sublayer/callout GUID из ревизии `63be0ebf9bec92bfba95ef3d6729c375aa9af84e` и считает связанные видимые фильтры. Он использует read-only транзакцию WFP, запросы по ключам и перечисление страниц; не открывает устройство драйвера, не отправляет IOCTL и не меняет службы/фильтры. Результат — короткий JSON без условий фильтров и сетевых адресов. Таймаут, ошибка API/доступа, неполный вывод или отсутствие помощника блокируют наблюдение. Объекты при остановленной службе блокируют дальнейшую подготовку. Все запросы могут быть выполнены только при явно разрешённом runtime; в этом шаге помощник лишь скомпилирован.

Поле `wfp_detachment_observed` означает сочетание остановленной/отсутствующей службы и отсутствия наблюдаемых известных объектов. Это ограниченное свидетельство: WFP перечисляет только доступные для чтения фильтры ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/fwpmu/nf-fwpmu-fwpmfiltercreateenumhandle0)); GUID ещё нужно связать с фактически проверяемой сборкой. `version_switch_ready` и `interception_cleanup_verified` остаются `false`. `current_driver_preparation_allowed` относится только к перечисленным проверкам обычного Driver-прогона, а прежний `PASS_CLEAN` ограничен отсутствием GUI/CLI и состоянием службы. В [контракте WFP-драйвера проверенного SHA](https://github.com/InterceptSuite/ProxyBridge/blob/63be0ebf9bec92bfba95ef3d6729c375aa9af84e/Windows/driver/src/ProxyBridgeDrv_ioctl.h) нет операции чтения флага enable/config. Далее нужны происхождение сборок и готовность legacy CLI с буферизованным stdout; безопасная альтернатива переключению на месте — последовательные чистые состояния одной VM.

Перезагрузка завершилась: загрузка 2026-09-29 13:02:35 UTC, активный TESTSIGNING подтверждён системным API (бит 0x02); результат — artifacts/machine-setup/after-restart.json. Разрешение на необходимую перезагрузку получено. Журнал — `artifacts/machine-setup/354073f8a5b344bba0008cc74537338a.log`. Постоянная ExecutionPolicy не менялась; обход требовался только для процесса запуска скрипта. Ниже сохранены исходное наблюдение и инструкция.

Пользователь разрешил TESTSIGNING и перезагрузку при необходимости 2026-09-29. При чтении состояния этой машины: текущий процесс не повышен, доступ к BCD запрещён, реестр Windows сообщает `UEFISecureBootEnabled=1`. `Confirm-SecureBootUEFI` также отказал из-за привилегий. Фактический флаг TESTSIGNING не установлен этим шагом и не подтверждён; перезагрузка не выполнялась.

Для включения требуется сначала отключить Secure Boot в настройках UEFI тестовой машины, затем из PowerShell администратора выполнить:

```powershell
& C:\src\ProxyBridge-TestLab\scripts\Set-DriverTestSigning.ps1 -Mode Enable
```

Скрипт проверяет Secure Boot, вызывает `bcdedit /set testsigning on`, читает BCD обратно и оставляет перезагрузку отдельным действием. Для возврата — `-Mode Disable` и перезагрузка. Скрипт Enable выполнен и перезагрузка завершена; повторное включение не требуется. Драйвер следует подписать тестовым сертификатом: TESTSIGNING не заменяет подпись, особенно при включённой Memory Integrity/HVCI ([Microsoft](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/the-testsigning-boot-configuration-option)). HVCI, BitLocker и другие параметры этим скриптом не меняются. Перед A/B необходимо зафиксировать одинаковое состояние этих настроек в обеих сериях.
