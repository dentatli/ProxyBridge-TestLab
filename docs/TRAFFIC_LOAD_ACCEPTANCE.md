# Приёмка высокой и длительной нагрузки

Актуально на 2026-10-14. Нагрузку запускает пользователь из TestLab от имени администратора: http://127.0.0.1:5205 → Testing → remote → «Трафик, скорость, нагрузка и стабильность». Выбрать проверенную сборку «актуал» (bundle a677580820ee370bef9aad59e3de6cf9eb7d5c672ccf9ec4c9b112753983ab2c), Ubuntu root@192.168.0.180. Выполнить «Проверить / подготовить runtime»; продолжать только при READY и совпадении установленного bundle. Если требуется обновление, применить именно свежий план и проверить READY повторно.

WinDbg должен оставаться закрытым, диагностические прогоны не должны использовать VM. Галочка WinDbg удалена из пользовательского интерфейса; для совместной рабочей VM согласование диагностических и нагрузочных запусков остаётся организационным правилом. Оставить Windows/Ubuntu включёнными и доступными на весь срок; питание и системные настройки TestLab сам не меняет. Не запускать одновременно другие продуктовые контроллеры. Оценка времени приблизительна: подготовка, сбор доказательств и завершение добавляют время к полезной нагрузке.

## Текущий допуск

Сбор финальных метрик исправлен: управляющее TCP-соединение устанавливается и аутентифицируется до включения продукта; каждый снимок имеет свежий challenge/flow ID и проверяемую HMAC-подпись. Нагрузочные соединения создаются обычными сокетами после старта продукта. Служебный канал не добавляет proxy-flow доказательств. Потеря канала не подменяется кэшем, результат остаётся FAIL.

Короткая очередь 20261014-084943-b57add856c9e4bb8bcec0ea0fbe3aef0 подтвердила TCP и HTTPS, но UDP-connected и mixed завершились FAIL: UDP 2256/0 и 2035/0 соответственно. При остановленном продукте отдельные UDP component checks получили 95/95 напрямую и 95/95 через явный SOCKS5. Это подтверждает эти два серверных пути, но не доказывает конкретную причину сбоя продуктового UDP. Итоговый runtime f187aca49181d3d5148be23a36e40e65911f7d35a5a5afe15875bf48bc25a371 установлен READY; повторный TCP 20261014-085548-2fbd9046d5084804abc38656d688463d на нём COMPLETE с route/cleanup=true. HIGH/длительная стабильность ещё не приняты. Старые ошибки Direct/WSA10053/10054 сохраняются в свидетельствах; предварительное соединение метрик не является исправлением Direct-пути ProxyBridge.

## Последовательность запуска

1. Снять прежнее выделение сценариев. Сначала выбрать только «TCP в обе стороны одновременно», HIGH, SHORT; запустить и дождаться результата, подтверждённого маршрута и очистки. HIGH для этого сценария означает 16 параллельных потоков в течение 6 секунд; это стартовая проверка, не длительная приёмка.
2. Если первая проверка прошла, повторить тот же сценарий HIGH, LONG: 16 потоков, 120 секунд полезной нагрузки. Затем отдельно «Задержка TCP под нагрузкой», HIGH, LONG: baseline, нагрузка (16 duplex-потоков и echo-проба), recovery; примерно 6 минут плюс подготовка. Для оценки соединений отдельно «Соединения TCP и восстановление», HIGH, LONG: baseline, 64/256/640 удерживаемых TCP-соединений с echo-пробой, recovery; примерно 10 минут плюс подготовка. Не объединять их со всем каталогом на первом запуске.
3. Для очереди дольше 5 минут включить явное разрешение длительного запуска. На первой приёмке оставить безопасное продолжение очереди после ошибки выключенным: сначала изучить первый отказ. Если включить продолжение позже, исходный FAIL сохраняется, следующий case допускается только после подтверждённой очистки/восстановления.
4. Смешанные «Стабильность, нагрузка и восстановление» и «Длительный прогон 24/48/72 часа» пока не использовать для подтверждения стабильности: оба обязательно включают UDP, который сейчас не проходит. Они не имеют режима TCP-only. Сначала требуется отдельная приёмка исправленного UDP-пути. Обходить failure/route gates нельзя.
5. После устранения UDP начать со «Стабильность, нагрузка и восстановление», HIGH, LONG: 8 интервалов по 120 секунд плюс baseline/recovery, всего около 20 минут и подготовка. После успешной очистки выбрать только длительный soak, HIGH, 24 h; затем по необходимости 48 h или 72 h. В UI для soak SHORT/NORMAL/LONG отображаются как 24/48/72 h, а не 6/30/120 секунд. HIGH: 16 duplex-потоков, 16 UDP-потоков с целевым темпом 1000 пакетов/с на поток и echo-проба в каждом минутном интервале. Это целевой темп, фактический может быть ниже; baseline/recovery и сбор доказательств добавляют время к 24/48/72 часам.

Если поток остановился, возникла ошибка или нужно закончить вручную, использовать «Остановить и очистить», дождаться окончания и проверить cleanup_verified. Ручная остановка означает CANCELLED и не доказывает завершение всего сценария. Не возобновлять старую попытку: следующий запуск создаёт новую.

## Что сохранить для разбора

Сообщить ID попытки и выбранные сценарии/нагрузку/длительность. В Results сохранить JSON истории; CSV полезен для сравнения, но не заменяет полные доказательства. Не удалять каталог `%LOCALAPPDATA%\ProxyBridge-TestLab\traffic-lab\<ID>`: attempt.json, case reports, raw JSON, private CLI console JSONL; для soak также raw.json.stages.jsonl. Console capture ограничен 4 MiB: после достижения лимита сохраняется prefix и общий stream SHA/счётчики, полный текст долгого прогона не обещается. Приватные файлы не отправлять в Git и публичные сообщения.

При разборе проверить complete/route_verified/cleanup_verified, фактические/пропущенные этапы, финальные подписи и identity, соответствие SHA raw/journal/console, TX/RX, TCP connect/echo p50/p95/p99, скорость baseline/load/recovery, UDP потери/истечение/ошибки отправки, тренды CPU/RSS и ресурсов ОС. Одного зелёного workload недостаточно без route и cleanup. RSS/CPU процесса и всей ОС различаются; отдельного точного счётчика ресурсов драйвера нет. Пропуски наблюдений нельзя считать нулевым потреблением или успешной доставкой. После запуска пользователь сообщает ID — сохранённый результат проверяется отдельно.
