# Простой путь запуска: проект интерфейса

Проект 2026-09-28. Основной сценарий работы согласован по целям, но этот экран ещё не реализован. Источник ограничений продукта: [официальная настройка ProxyBridge для Windows](https://interceptsuite.com/docs/proxybridge/configuration-windows/). Текущая реализация: `ui/ProxyBridge.TestLab.Ui/wwwroot/index.html`, `app.js`, `Services/RunReadinessService.cs`, `Services/SettingsSchema.cs`.

Актуализация 2026-10-05: одностраничный поток ниже заменён [планом отдельных страниц, именованных сборок, выбора тестов и таблицы сравнения](INTERFACE_PLAN_2026-10-05.md). Этот документ сохраняет историю первоначального дизайна.

## Главный экран

Первое открытие показывает одну последовательность: **Подключение → Тестирование → Проверка и запуск → Результат**. В шапке — готовность ProxyBridge, переключатель **Русский / English** и кнопка «История результатов». Отдельный технический каталог остаётся в разделе «Дополнительно».

```
Подключение                         Тестирование                Проверка и запуск
[Прокси на этом ПК | удалённый]  →  [Быстрая проверка ▾]  →  [Начать]
 SOCKS5 · 127.0.0.1:10808            [Сравнение версий]          Что будет проверено
 Контролируемый получатель           [Нагрузка и ресурсы ПК]     Что недоступно и почему
 [Проверить подключение]            [Загрузка / отправка]
```

С первого выпуска нужны два языка: русский и английский. Переключение языка меняет навигацию, поля, ошибки, статусы, объяснения результатов и экспортируемый пользовательский отчёт; внутренние ID сценариев и машинные статусы остаются стабильными. Выбор языка сохраняется в настройках пользователя. Примеры ниже написаны на русском; английские строки готовятся одновременно с реализацией экрана.

## Шаг 1. Подключение

Пользователь выбирает **где находится прокси**, затем его тип (SOCKS5 или HTTP), адрес и порт. При выборе «На этом ПК» предложить `127.0.0.1` как адрес прокси, но разрешить другой локальный адрес; «Удалённый» принимает внешний адрес/имя. Размещение — свойство прокси, не получателя. Throne не упоминается как обязательный компонент.

Ниже показать **контролируемый получатель**. Выбора произвольного интернет-адреса для бенчмарка нет: получатель должен независимо подтверждать доставку, целостность и маршрут. В локальном режиме — получатель на Windows-ПК; в удалённом — управляемый получатель на другой машине, включая Linux-узел. Прокси и получатель могут физически находиться в разных местах, поэтому готовность определяется по фактическому пути каждого теста. Для полностью локальной схемы требуется отдельный контролируемый Windows-получатель и способ доказать прохождение через локальный прокси. Это новая работа, не способность текущего runner.

Проверка подключения по кнопке показывает: «Прокси доступен», «Прокси поддерживает UDP ASSOCIATE» и «Получатель доступен по ожидаемому пути». Каждая строка — наблюдаемое свойство с собственным статусом, а не общая галочка. HTTP-прокси может выполнять TCP-сценарии; UDP `PROXY` через него нельзя считать доступным. Если SOCKS5 не поддерживает UDP ASSOCIATE, скрыть UDP-прокси нагрузки из обычного выбора и показать причину. По документации ProxyBridge localhost назначения по умолчанию идёт напрямую: локальный получатель на `127.0.0.1` не считается доказательством PROXY.

Секреты вводить только при необходимости; хранить защищённо, не возвращать в API и не показывать в отчёте. Настройки ProxyBridge, клиента и получателя показывать кратко: название, проверенное состояние и ссылку «Изменить».

## Шаг 2. Тестирование

Первый ряд карточек: **Быстрая проверка**, **Сравнение версий**, **Загрузка и отправка**, **Нагрузка и ресурсы ПК**, **Длительная работа**. Карточки показывают длительность, TCP/UDP, нужные компоненты и доступность в выбранном подключении. Пока backend готов только для части карточек, остальные пометить «Планируется» или «Требует настройки»; не выводить их как запускаемые.

«Быстрая проверка» — проверить выбранный маршрут, блокировку, доставку и отсутствие неожиданного прямого соединения; она не выдаёт результат скорости. «Сравнение версий» — два указанных экземпляра/сборки ProxyBridge, одинаковый сценарий, прогрев и повторы, включая расход ресурсов ПК. «Загрузка и отправка» — объём и число потоков с проверкой целостности. «Нагрузка и ресурсы ПК» показывает пропускную способность вместе с загрузкой CPU и памяти ProxyBridge, генератора и всей Windows-системы, с измерением фона до и после. «Длительная работа» добавляет динамику потребления и ошибки по времени. Пользователь выбирает понятный сценарий; технические ID показываются только в подробностях запуска.

Для первого сравнения карточка предлагает «Последний коммит Driver ↔ 4.0.0». Перед запуском TestLab показывает кратко: какие правила и нагрузки доступны на обеих версиях, а какие нельзя сравнивать из-за различий функций. На основном экране пользователь видит названия версий; точные commit SHA и идентичности файлов остаются в деталях. Автоматическое переключение установленных драйверов не считать готовым, пока не подтверждены безопасная остановка, очистка и возврат исходного состояния.

Параметры карточки — лишь значимые: длительность, объём, параллелизм и протокол, когда он применим. Профиль «Обычно» задаёт разумные ограниченные значения; «Настроить» открывает детали. Не включать все протоколы одним нажатием, если текущая конфигурация не подтверждена для них.

## Шаг 3. Проверка и запуск

Одна сводка: «Будет проверено», «Готово», «Нужно исправить». Для каждого препятствия — одно понятное действие: например «Получатель недоступен» или «Этот SOCKS5 не поддерживает UDP». Служебные nonce, хеши, receipts и сроки используются внутри системы и не перегружают экран. В реальном запуске сохраняется явное подтверждение запуска продукта и трафика, защита от параллельных прогонов и отмена с очисткой.

Режим «Предпросмотр на фикстурах» вынести в «Дополнительно» и ясно помечать: он проверяет работу TestLab, не ProxyBridge. Готовность считать отдельно для выбранного сценария и топологии. Неприменимый Linux-gate не должен блокировать локальную схему, но его снятие требует полноценного другого доказательства маршрута, а не скрытия предупреждения.

## Шаг 4. Результат и сравнение

Основной экран — четыре понятных показателя: **Работает правильно?**, **Скорость**, **Нагрузка на ПК**, **Стабильность**. Для A/B показать изменение скорости и потребления ресурсов, а также короткую оценку сопоставимости условий. Если путь или доставка не доказаны, показать «Недостаточно данных» с одной понятной причиной; не выдавать наблюдаемую разницу за подтверждённое изменение ProxyBridge.

Кнопка «Подробности» открывает графики скорости и потребления ресурсов, ошибки и список сценариев. На главном экране нет хешей, внутренних ID, receipts и длинных диагностических статусов. Для последующего аудита служебные идентификаторы и доказательства сохраняются в отчёте/экспорте, но не отвлекают обычного пользователя. Исторический результат сохраняет использованную топологию, прокси и ограничения; разные условия помечаются как несопоставимые.

## Что переиспользовать и что изменить

| Уже есть | Использование | Требуемая работа |
|---|---|---|
| Каталог и `scenario_id` | Сохранить как внутренний контракт и расширенный каталог | Добавить понятные имена/группы и проекцию карточек; не менять ID ради подписи |
| SettingsStore и DPAPI | Хранение параметров и защищённых значений | Новая модель типа/расположения прокси и получателя; условная готовность вместо обязательного SSH |
| RunCoordinator, job store, SignalR, отмена | Прогресс и остановка | Сохранить жизненный цикл; добавить выбранную топологию и параметры нагрузки в идентичность задания |
| Readiness, immutable preflight, evidence | Основа проверки перед реальным запуском | Ветви для локального контролируемого получателя и удалённого узла, с достаточными независимыми доказательствами |
| Report viewer и export | Детали и аудит | Добавить A/B, CPU/память ПК, сопоставимость условий и простой пользовательский итог на двух языках |
| Server Setup | Дополнительная настройка управляемого Linux-узла | Убрать из обязательного пути локального режима, оставить по явному выбору узла |

Текущее `RunCreateRequest` содержит только `mode`, `scenario_ids`, `confirmation_nonce`. Оно не описывает ни топологию, ни параметры A/B; для нового потока нужен расширенный контракт задания. Текущий `RunReadinessService` требует `ServerReady` для любого реального прогона, а `SettingsSchema` — Linux SSH-поля. Поэтому простое изменение HTML дало бы ложное обещание локального режима. Предлагаемый порядок реализации: модель подключения → проверяемая готовность и доказательства → выбор нагрузок → экран → A/B-отчёт.

На этом этапе не менялись runner и UI. Конкретные значения по умолчанию и форма сравнения версий остаются решениями при реализации; наличие русского и английского языков, контролируемого получателя и измерения ресурсов ПК уже определено.
