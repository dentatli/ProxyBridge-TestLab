## Что найдено в выбранной версии

Проверен исходный upstream driver commit 63be0ebf9bec92bfba95ef3d6729c375aa9af84e, соответствующий выбранному baseline. HEAD локального C:\src\ProxyBridge-Driver — другая ревизия 137d1286, поэтому выводы ниже получены по закреплённым GitHub исходникам, а не по текущему локальному checkout. Это анализ кода, не подтверждённый эксперимент. Не переносить выводы на 4.0.0 или будущую beta без проверки её реализации.

- [pbdrv_state.c](https://github.com/InterceptSuite/ProxyBridge/blob/63be0ebf9bec92bfba95ef3d6729c375aa9af84e/Windows/driver/src/pbdrv_state.c): очередь событий PB_EVENT_RING=2048 использует один свободный слот (2047 непрочитанных событий). При заполнении вытесняет старое событие; это потеря наблюдений для журнала, а не удаление действующего соединения.
- В том же файле UDP_MAP_SIZE=2048 — корзины хеш-таблицы со связанными списками. Узлы выделяются из nonpaged pool; общего численного лимита узлов и отдельного удаления/таймаута потока в этом файле нет. UdpMapClear освобождает все узлы; в закреплённом ProxyBridgeDrv.c найден вызов при выгрузке драйвера, SET_CONFIG и DISABLE карту не очищают. Нужна проверка роста занятой памяти при последовательном создании уникальных endpoint и поведения при повторном использовании портов. Само превышение 2048 потоков не доказывает переполнение.
- [ProxyBridgeDrv.c](https://github.com/InterceptSuite/ProxyBridge/blob/63be0ebf9bec92bfba95ef3d6729c375aa9af84e/Windows/driver/src/ProxyBridgeDrv.c): TCP передаёт исходный адрес через redirect context WFP; UDP записывает адрес в карту. UdpMapPut не возвращает статус выделения памяти, перенаправление продолжается. При неудаче выделения возможна утрата нужного соответствия; точный результат доставки необходимо проверять на стенде, не объявлять из одного анализа.
- [pb_relay_tcp.c](https://github.com/InterceptSuite/ProxyBridge/blob/63be0ebf9bec92bfba95ef3d6729c375aa9af84e/Windows/src/relay/pb_relay_tcp.c): TCP использует сокеты, память и потоки на соединения; при неудаче malloc/CreateThread закрывает принятое соединение. Вероятные ограничения под нагрузкой — ресурсы, очередь принятия и стоимость обработки, а не единый заполненный массив.
- [pb_conntrack.c](https://github.com/InterceptSuite/ProxyBridge/blob/63be0ebf9bec92bfba95ef3d6729c375aa9af84e/Windows/src/relay/pb_conntrack.c): таблицы со списками, пользовательские allocations, удаление устаревших записей и отдельный ограниченный журнал. Наличие этой таблицы в Core не означает, что каждый TCP поток driver хранится именно в ней.

Ожидаемое хорошее поведение: сохранность уже установленных потоков, понятный отказ новым при достижении предела, отсутствие обхода правил/смешивания данных, восстановление после снижения нагрузки. Отказы и потери журналов показывать отдельно. Возможные задержки, рост CPU/RAM, ошибки новых соединений — гипотезы до измерения; зависание/падение не считать штатным следствием насыщения.

## Методика будущего сценария

1. Прямой путь при выключенном продукте и путь через SOCKS5, как в остальных обычных тестах. Пользователь уточнил: OFF / UNRULED / PROXY — отдельный тест «Три режима» со своей длительностью и нагрузкой, поэтому UNRULED не добавлять в тест насыщения. Для каждого уровня одинаковые получатели, payload, темп, удержание и идентификация данных. Порядок чередовать; driver/4.0.0 переключать только по согласованной процедуре перезагрузки.
2. Постепенно увеличивать одновременно удерживаемые TCP-соединения либо UDP сокеты/потоки. Каждое соединение регулярно обменивается уникальными данными, чтобы проверить старые потоки одновременно с созданием новых. Считать попытки отдельно от действительно работающих потоков.
3. Отдельно повышать скорость открытия/закрытия: переполнение очереди событий зависит от событий/сек и скорости чтения, а не только от числа удерживаемых соединений. Повторить несколько циклов с фазой восстановления, наблюдать накопление памяти, ошибок и время возвращения к базовой задержке.
4. TCP/UDP, IPv4/IPv6, один/разные получатели — разные проверенные профили. UDP shared destination обязательно проверяет известное смешивание потоков; DISTINCT не выдавать за исправление этого дефекта. Уникальные client/message IDs, содержимое, отправитель и адрес получателя подтверждаются независимо от журнала продукта.
5. Отдельно наблюдать ресурсы продукта, генератора, SOCKS5 и получателя; общую CPU/RAM, потоки/handles и kernel nonpaged pool — только при доступном подтверждённом сборе. Системный pool не называть памятью только ProxyBridge; CPU CLI не называть CPU драйвера. Не маскировать потолок самого генератора, нехватку портов/TIME_WAIT, лимиты ОС/прокси как переполнение продукта.
6. Ограничить максимальные уровни, длительность и объём журналов, задать прекращение при нехватке памяти/места и повторных ошибках; не добиваться падения ОС. Кооперативная остановка и проверенная очистка, все частичные/failed попытки сохраняются. Новый тяжёлый запуск вручную выполняет пользователь после подготовки команды и оценки времени.

Показывать уровень предложенной нагрузки и подтверждённых активных потоков, успешность открытия и время установления, RTT p50/p95/p99, таймауты/сбросы/потери/повреждение/неверный маршрут, ресурсы и восстановление. Потери логов не равны потерям пакетов. Если занятость внутренней таблицы не наблюдается, итог — «Поведение при N подтверждённых потоках», а не «Таблица точно переполнена». Максимальную ёмкость не объявлять по одному достигнутому уровню или отказу генератора.

Последние результаты брать по сборке + виду теста + точным условиям/методике, история не переписывается. Известные дефекты остаются видимыми; будущий PASS допускается только по новой фактической проверке. Конкретные уровни/параметры и reuse готового генератора (ctsTraffic для TCP там, где подходит) определить при реализации, без новой самописной сетевой библиотеки ради этого плана.
