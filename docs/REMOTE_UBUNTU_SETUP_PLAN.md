# Удалённая Ubuntu: настройка и допуск тестов

Согласованный пользовательский сценарий на 2026-10-07. Интеграция в новый интерфейс ещё не завершена. Основной план — [DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md).

## Сценарий интерфейса

1. После выбора «На удалённом узле» появляется блок SSH-настройки. Выбранные тесты, их длительность и нагрузка сохраняются.
2. «Сгенерировать SSH-ключ» создаёт отдельный ключ TestLab. Публичный ключ показывается с кнопкой копирования и инструкцией добавить его пользователю `root` в `~/.ssh/authorized_keys` на Ubuntu. Закрытый ключ остаётся на Windows вне Git/журналов, с доступом владельца и SYSTEM. Существующий ключ используется повторно; замена требует отдельного явного действия.
3. Пользователь вводит IP и необязательный SSH-порт (по умолчанию 22), пользователь SSH — `root`. При первом подключении показывается отпечаток сервера для подтверждения; далее используется сохранённая привязка. Изменившийся ключ не принимается автоматически.
4. «Автоматическая настройка» проверяет платформу, устанавливает необходимые компоненты TestLab и проверяет готовность. Эта кнопка разрешает настройку; обычный сценарий не требует отдельных ручных create-plan/apply. Точный внутренний план и результаты сохраняются для диагностики.
5. «Проверить соединение» проверяет уже настроенный узел: SSH, установленные компоненты и фактический контрольный обмен. Кнопка не устанавливает пакеты и не исправляет конфигурацию. При необходимости предлагает автоматическую настройку с конкретной причиной.
6. После успешной проверки показывается «Готов к тестированию», становится доступен запуск удалённых тестов. При отсутствии соединения запуск запрещён.

Уточнение пользователя 2026-10-08: поддержка начиная с Ubuntu 22.04. Целевая матрица нового мастера — Ubuntu Server **22.04, 24.04 и 26.04 LTS**, с актуальными обновлениями своего выпуска. Точный `VERSION_ID` проверяется по allowlist; промежуточные и будущие выпуски автоматически не допускаются. Новый LTS добавляется после проверки зависимостей и контролируемого обмена; пересмотр списка перед окончанием стандартной поддержки старейшего выпуска. Выпуски и сроки сверены с [официальным циклом Ubuntu](https://ubuntu.com/about/release-cycle) и [списком выпусков](https://ubuntu.com/project/docs/release-team/list-of-releases/). Допуск по этой матрице ещё не реализован; Ubuntu 22.04.5 диагностического стенда по-прежнему не является свидетельством готовности нового режима. Историческая поддержка Debian не определяет новую матрицу.

## Проверка готовности

Успешный SSH-вход недостаточен. Нужны проверенные версия Ubuntu, ресурсы, хеши компонентов, состояние собственных служб/портов, обмен с проверкой данных напрямую и через выбранный SOCKS5, необходимые TCP/UDP-возможности, доступность CPU/RAM и завершение проверочных процессов.

Результат привязывается к IP, SSH-порту, ключу сервера, конфигурации маршрута и версиям компонентов. Изменение значимых настроек аннулирует готовность. После перезапуска приложения нужна повторная проверка. Показываются этап, причина ошибки и время последней успешной проверки; состояния: «Не настроен», «Подключение», «Настройка», «Проверка», «Готов», «Недоступен», «Ошибка».

Периодическая проверка недоступности запрещает новые запуски. Серверная часть повторно проверяет готовность перед подготовкой и перед каждым тестом очереди; отключённая кнопка не заменяет этот запрет. При потере связи во время теста сохраняются неполный результат и причина, очередь останавливается. Новая успешная проверка восстанавливает допуск. Прежний успешный результат не подставляется вместо новой ошибки/отмены.

## Сервер и тесты

Root используется для установки/управления, тестовые службы работают с ограниченными правами. Настройка повторяемая: корректный комплект проверяется без переустановки, несовпадающий обновляется с отчётом и восстановлением принадлежащих TestLab файлов/служб. Не заменять глобальный firewall и не останавливать чужие службы; конфликт портов — ошибка. Источники доступа определяются по фактическому маршруту; SSH-адрес не считается автоматически адресом выхода SOCKS5.

Цель — весь каталог удалённых тестов: задержка, передача, отдельные «Три режима», соединения/восстановление и остальные запланированные сценарии, с индивидуальными длительностью и нагрузкой. Каждый удалённый контроллер/протокол проверяется до включения. Пока возможность не реализована, конкретный тест заблокирован с объяснением: статус готовности узла не делает незавершённый тест работающим.

SOCKS5 на удалённом узле и удалённый получатель — разные роли; конфигурация и результаты описывают обе. При NAT сопоставление потоков требует уникальных идентификаторов и проверенных данных, а не равенства исходных IP/портов. История сохраняет топологию и условия; выборочная таблица использует последние попытки и не смешивает несовместимые условия.

## Текущее состояние и порядок работы

| Область | Уже есть | Предстоит |
| --- | --- | --- |
| Технический интерфейс | ServerTransport, ServerProvisioningService, доверие/готовность, API validate/plan/apply | Новый сценарий, root и явная матрица Ubuntu |
| Новый интерфейс | Выбор remote, запрет REMOTE_CONTROLLER_PENDING | Генерация ключа, две кнопки, статусы, проверки допуска |
| Linux-диагностика | Четыре прямые CTS-передачи Windows → Linux: 2 MiB без ошибок данных | TCP push/data-получатель ещё не полный удалённый каталог |
| Контроллеры/результаты | Локальные сценарии, имена сборок, история/последние попытки | Удалённые пути, протоколы, метрики, очистка и условия сравнения |

Ближайший шаг расследования — парный опыт с локальным и Linux-получателем, сохраняя локальный SOCKS5 и исходный Core. Уже подтверждены отказ первого SYN при давлении на очередь приёма, повтор подключения, STATUS_NOT_FOUND при запросе redirect context и последующее закрытие Core. Точный внутренний механизм утраты контекста Windows ещё не установлен. Для интерпретации нужны сопоставленные цепочки и воспроизведение исходного триггера в обоих вариантах; отсутствие ошибки без триггера не доказывает исправление.

Затем интегрировать мастер и удалённые контроллеры. Приёмка: свежая и ранее настроенная Ubuntu, повторная настройка, неверный ключ/порт, неподдерживаемый выпуск, конфликт порта, изменённый ключ сервера, отключение/возврат связи. Проверить запрет через UI и прямой API, свежую проверку перед каждым тестом, историю ошибок, отсутствие закрытого ключа в отчётах/Git. Для каждого включённого теста подтвердить маршрут, целостность, заявленные метрики и очистку.

Текущие Windows/Linux — VM на одном физическом ПК: это вынос из Windows loopback, не независимое оборудование. HTTP proxy для Codex сохраняется. Исходники/документация сохраняются commit/push; секреты остаются вне Git. Самостоятельные проверки ожидаемой длительности менее пяти минут разрешены пользователем; длительный набор нельзя делить ради обхода ограничения.
