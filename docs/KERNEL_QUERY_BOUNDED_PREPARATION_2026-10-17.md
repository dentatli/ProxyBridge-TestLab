# Подготовка отдельной серии 4 → 64 → 256 → 4 с двумя query-точками

Это следующий опыт после [успешной четырёхсоединительной пробы логгера](KERNEL_QUERY_SESSION_FOUR_RESULT_2026-10-17.md). Новый метод `redirect-kd-query-bounded-v1` ограничен 328 соединениями. После подготовки пользователь согласовал один конкретный Run; он ещё не выполнен. Пользователь также уточнил: во время общения с этим чатом считать VM свободной от параллельной работы, не переспрашивать это без новых противоречащих сведений. Обе точки 3/4 в конце последнего user console отключены, затем введён отдельный `g`. Их нынешнее состояние перед новым включением проверяет пользователь.

## Контракт и цель

- Фазы: baseline 4, load-64, load-256, recovery 4 в одном сеансе CLI. Этапа 640 нет. По 512 KiB на соединение, hold 8 s, ConnectEx/pending 32, original listener/delay 0, ровно один исходный query Core. Те же пинованные CLI/Core/driver, без сборки и установки.
- Только существующие точки 3/4 с прежними actions QUERY_READ/QUERY_STATUS. Не загружать stage повторно и не добавлять CREATE/FREE/NBL или общесистемные точки.
- Ожидание клиента ограничено 120000 ms, бюджет фаз 240000 ms. Ожидание ограничивается оставшимся бюджетом; проверки между фазами запрещают начало следующей после его исчерпания. Это не жёсткий предел всей команды: хеширование, старт CLI/fixtures и завершение/очистка имеют отдельные интервалы, остановленная debugger VM также не гарантирует своевременного выполнения контроллера.
- Перед каждой фазой минимум 2 GiB свободной физической RAM и 256 MiB диска. Нехватка ресурсов, timeout или вынужденная очистка прекращают следующие фазы. Измеренные native TCP отказы сохраняются; при штатном завершении фазы серия продолжается к recovery, а не скрывает отказы повтором.
- Новый флаг `-BoundedLoadReviewed` — ручное подтверждение конкретного опыта, не автоматическое разрешение. Контроллер сохраняет mutex/lease, проверки прежних interrupted/legacy runs, пинованные файлы и boot estimate ±1 s от проверенной регистрации. После перезагрузки требуется новая проверка состояния, не обход guard.

Ищем конкретный исходный Core query 10022/native failure и соответствующие QUERY_READ (record) / QUERY_STATUS (NTSTATUS). Отчёт по VM-файлам оставляет kernel console непроверенным: `ntstatus_observed=false`, `root_cause_proven=false`. Даже наблюдение NULL+C0000225 установит состояние при запросе, но не механизм потери записи. Создание, прикрепление и освобождение потребуют следующего обоснованного опыта.

Привязка KD↔Core остаётся условной на полноту console, PID/TID и порядок неперекрывающихся query. В этих actions нет независимых socket/seq/TCP tuple/общего QPC; повторяющийся stack scope не является flow ID. При параллельных интервалах, пропусках или неоднозначности не объявлять корреляцию доказанной. Отсутствие отказа под KD не доказывает исправление: в четырёхсоединительной пробе query занимал 250–317 ms с паузами debugger, и расписание меняется.

## Отдельные исходники

`scripts/Invoke-KdQueryBounded.ps1`, `scripts/Invoke-KdQueryBoundedWorkload.ps1`, `modules/KdQueryBoundedConnectionLoad.psm1`, `src/pb_prepare_kd_query_bounded.py`, `src/pb_kd_query_bounded_report.py`. Старые Session/Probe/Control sources и preparations не изменяются. Новый module сохранён UTF-8 BOM для Windows PowerShell 5.1.

В новый kit копируются отдельный Python runtime без bytecode caches, три пинованных product binaries и debugger evidence: исходная регистрация, stage/profile, raw user console последней пробы и его отдельный review. Frozen manifest хеширует источники, helpers, runtime и evidence; копирование не означает загрузку продукта или выполнение debugger actions.

## Проверки без продукта

PowerShell 5.1 и 7 разобрали три новых PS-файла и проверили preset. Частные проверки подменили cohort и запись receipt только в памяти: получили 4/64/256/4, а при имитации resource bound на 256 — остановку до recovery. Настоящий cohort, workers, CIM и сеть в этих проверках не вызываются.

Частная синтетическая копия старого полного capture с удалённой фазой 640 и её query lines проверяет только reporter: 328 query, 32 сохранённых native/API10022, kernel pending. Это не новый Run и не свидетельство отказа под KD. Копии с прежними четырьмя и полными 968 reporter отвергает как неполный/чужой контракт фаз. Первая попытка построить fixture не учла префикс `[LOG]` перед query label и получила UNASSIGNED_OR_DUPLICATE_QUERY_METADATA; исправлена только частная фильтрация копии, не продукт/reporter/оригинал.

Аудит: `artifacts/diagnostics/pb-kd-query-bounded-review-20261017/`. Приватные captures/kit/console не добавляются в Git. 114 защищённых старых исходников и файлов captures проверены неизменными после подготовки.

## Стоп-пункт

Комплект готов, один USER Run согласован. Следующий шаг — USER inventory bl/bpcmds/g и review до enable/Run; повторно согласие и отсутствие параллельной работы не спрашивать. Пользователь управляет WinDbg на физическом хосте; агент его не трогает. Перед каждым Break и включением каждой точки предупреждать, что останавливается/может останавливаться вся PB-BUILD-W11-25H2, включая Codex и RDP. Recovery заранее сохранить на физическом ПК: `bd3`, `bd4`, `bl`, затем отдельный `g`; каждую команду вводить отдельно даже после ошибки. Не повторять Run при ошибке, сохранить полный вывод. `.logopen` по предпочтению пользователя не нужен.
