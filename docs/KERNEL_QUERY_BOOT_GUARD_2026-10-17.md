## Что установлено

Старый guard сравнивает текущее CIM `Win32_OperatingSystem.LastBootUpTime` с сохранённой оценкой `2026-10-17T06:04:48.7518300Z`, допуск 1 s. В 12:16:06 местного времени CIM вернул `06:05:41.1579440Z`: разница **52.406114 s**. Следующее read-only наблюдение дало ещё более позднюю CIM-оценку `06:05:56.2253760Z`.

Последняя доступная запись System / Microsoft-Windows-Kernel-General / Event 12 имеет EventRecordID **16348**, StartTime **2026-10-17T06:04:46.5000000Z**, TimeCreated `06:04:46.6112030Z`, computer `PB-BUILD-25H2`. Следующая более старая запись запуска — 16 октября. Registry PrefetchParameters BootId = **112**. USER показал прежние адреса query-точек. Это согласуется с продолжением прежнего сеанса; сообщение guard само по себе не доказывает перезагрузку. Историческая CIM-оценка отличается от StartTime записи примерно на 2.25 s; исходного снимка Event 12/BootId на момент регистрации нет, непрерывная идентичность сеанса этим не доказана.

Ненадёжность сравнения меняющейся CIM-оценки с допуском 1 s установлена наблюдениями. Причина её изменения не установлена. Связь с остановками WinDbg, коррекцией часов или другим механизмом остаётся гипотезой. Значение просто не подменяется и допуск не расширяется ради прохождения.

## Отдельный вариант без изменения старого kit

Новые файлы: `modules/KdBootSessionEvidence.psm1`, `scripts/Invoke-KdQueryBoot.ps1`, `src/pb_prepare_kd_query_boot.py`. Старые Bounded wrapper/preparer и все 8291 frozen inputs/plan сохранены. Query workload/module/report, точки и нагрузочный контракт `redirect-kd-query-bounded-v1` остаются прежними. Новый prefix подготовки `pb-kd-query-boot-preparation-*` исключает приём старого kit новым wrapper.

Подготовка сохраняет raw XML последнего Event 12, извлечённые поля и BootId. Этот конкретный preparer ограничен рассмотренным сеансом: EventRecordID16348/BootId112/StartTime06:04:46.5/computerPB-BUILD-25H2. После нового boot нельзя просто переподготовить его на новые значения: требуется отдельный review. План дополнительно содержит `boot_binding` с frozen SHA файла `debugger-evidence/boot-session.json`.

При Run новый wrapper заново читает системные свидетельства и **точно** сравнивает computer/provider/event ID/record ID/StartTime/TimeCreated/BootId. Проверяет согласованность извлечённых полей с raw XML. Отсутствие источника, иной record/BootId или несогласованные данные запрещают запуск. CIM-оценка и время наблюдения записываются, но не служат ключом сеанса. Для сохранённых legacy/interrupted chronological gates используется StartTime записи запуска; остальные mutex/lease/gates сохранены. Текущий снимок сохраняется в новом run directory до workload.

Это привязка по журналу и реестру, не криптографический идентификатор boot и не защита от восстановления VM snapshot/подмены системных свидетельств. При очистке журнала/недоступности источников запуск может быть запрещён. Ограничения явно сохраняются; boot binding не доказывает загрузку конкретного driver или полноту lifecycle capture.
