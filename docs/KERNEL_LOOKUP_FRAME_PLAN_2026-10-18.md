# Lookup: проверка кадра и вызывающего кода перед новым профилем

Продолжение [офлайн-разбора lookup](KERNEL_LOOKUP_OFFLINE_2026-10-18.md). Новые точки и нагрузка не выполнялись. Продукт и старые комплекты не менялись.

По текущему дисковому `fwpkclnt.sys` проверены prologue/сохранение RDI/восстановление RDI. Три push и sub rsp,50h дают смещение return address +68h. Для рассматриваемых внутренних участков кандидаты расположения данных:

| Поле | Расположение |
| --- | --- |
| Сохранённый RBP вызывающего кода | rsp+58h |
| Сохранённый RBX вызывающего кода | rsp+60h |
| Return address | rsp+68h |
| Сохранённый RDI вызывающего кода | rsp+78h |

У подтверждённого вызова из TCP/IP caller RBX соответствует NBL, caller RDI — endpoint. Это условная интерпретация только после точного caller filter. Доступность памяти и значения в живом кадре ещё не проверены. Возможный общий guard диапазона rsp+58h/28h не заменяет отдельные guards для любых последующих разыменований. Никаких новых stack reads на target не было; старую неисправную точку17 не использовать.

Выявлена важная неоднозначность адреса возврата. В дисковом tcpip IAT call начинается на RVA1566f и заканчивается на15676; затем5-byte NOP, test EAX на1567b(+caf). Адрес после NOP нельзя автоматически считать return address фактически загруженного вызова: в прошлых live-листингах встречалась другая форма import call. Нужен текущий live-участок TCP/IP+с7d, прежде чем писать caller condition.

Участок fwpk+f3 формирует ранний NOT_FOUND. Участок +22e вычисляет статус после общего поиска **и при успехе, и при промахе**. Поэтому установка точки на +22e с условием r14b=0 сократит строки, но не устранит debugger traps успешного пути. Нельзя обещать две исключительно редкие точки, покрывающие обе группы, без дальнейшего выбора мест. Отдельный выход +2f5 относится к исчерпанию списка; он не покрывает общий случай, когда начальный поиск вообще не вернул список.
