Это three-modes, tcp-connections и 24 прикладные проверки TCP: WebSocket, четыре gRPC, HTTP/HTTPS/WSS/HTTP2 payload sweep, TLS, DNS TCP/TLS/HTTPS, SSH, шесть почтовых, MQTT/MQTTS/AMQP/AMQPS. Для них можно сопоставлять задержки и затраты процесса при указанной нагрузке. Один прогон каждого варианта не устанавливает устойчивое преимущество.

Пример сопоставимой работы: HTTP/2 payload sweep — **36000 подтверждённых транзакций у обоих**, темп 100/с на поток. CPU seconds процесса за нагрузку: WinDivert 9.21875, WFP 1.390625; это 0.2561 и 0.03863 CPU-с/1000 транзакций. Данный пример показывает снижение затрат наблюдаемого процесса в этой паре, но не полный расход ресурсов WFP.

TCP connections: оба выдержали 8/32/128 удерживаемых соединений плюс один probe. Пиковая память процесса при нагрузке: commit WinDivert 8.69 MiB/WFP 45.29 MiB, working set 11.14/45.53 MiB. Это реальные пики процесса, а не автоматически утечка или полная память драйвера.

## Ограничения численного сравнения

- **Скорость TCP:** WFP upload 2130.15 MiB/s, download 2064.63 MiB/s; WinDivert 323.44/210.73 MiB/s. CPU всего ПК WFP 99.75/99.83%. Это достигнутые end-to-end скорости локального стенда с генератором, relay и получателем на одной машине. Нельзя называть их пределом WFP или отношением максимальных скоростей двух архитектур. Низкий общий CPU WinDivert также не исключает насыщения одного потока/ядра или иного bottleneck. PROFILE — намеренно без фиксированного темпа, зелёного рейтинга нет.
- **Loaded RTT:** WinDivert probe лишь 51.93/с при цели 100, WFP 100/с, но CPU ПК WFP 99.91%; фоновые скорости тоже различаются. Это разные достигнутые нагрузки, сравнение задержек под одинаковым давлением не получено.
- **SFTP:** оба функционально PASS, но WinDivert 6832 транзакции (56.9–56.97/с на поток), WFP 8761 (72.9–73.13/с), цель 100/с. Эти значения описывают достигнутую работу; не подтверждают заданную нагрузку или причину ограничения. Не ранжировать CPU mean как при равной работе.
- **Flow rate:** нагрузочный интервал 1024/1158 успешных сессий, примерно 33.82/38.32 в секунду; плюс baseline/recovery дают общий счёт 1026/1160. Профиль содержит 50 ms обмена на сессию и два worker; это не maximum CPS. Setup p99 10.98/2.70 ms включает TCP и подготовку получателя. Счёт завершённых сессий в фиксированное время закономерно различается.
- **Стабильность:** WFP записал все 8 нагрузочных интервалов, WinDivert только 1 из 8. WFP CPU 98.29–99.93%; UDP подача в первых интервалах лишь 57.1–81/с вместо 100, хотя обмен при фактической подаче корректен. Поэтому WFP functional PASS не означает достижение всей задуманной нагрузки. Сравнивать средние/пики или продолжительность этих двух stability cases нельзя.
- Различие числа подтверждённых обменов допустимо для задания «работать N секунд», но полезную работу, долю ошибок и достигнутый темп надо рассматривать вместе. Разные объёмы не превращать в равные; нормализовать затраты по подтверждённой работе, где применимо. Signed memory last−first может быть отрицательным и не имеет победителя/относительного процента.

**Вывод:** исправления методики работают на полных данных: underload, CPU saturation, неполные окна и partial accounting различаются и исключаются из рейтинга. Эти прогоны пригодны для функционального сравнения и ограниченного сравнения 26 пар, но не для общего вывода «какая архитектура лучше во всём». Для честного сравнения loaded RTT/stability следующим отдельным изменением нужен одинаковый ограниченный фон, оставляющий запас стенду; для максимальной скорости — независимый запас генератора/приёмника. Kernel attribution, продуктовая диагностика и новые полные прогоны здесь не выполнялись.
