# Локальный получатель и метрики Windows-ПК

Контракт и состояние реализации, 2026-09-28. Требования: контролируемый получатель в обоих режимах, честный маршрут, бенчмарк скорости и потребления ресурсов ПК, краткий двуязычный итог. Основной путь UI: [INTERFACE_FLOW_2026-09-28.md](INTERFACE_FLOW_2026-09-28.md).

Первый ограниченный срез добавлен в backend: `LocalReceiverService` запускает существующий `pb_net_endpoint.py` через упакованный Python (или локальное dev-окружение), создаёт приватный журнал одной попытки, проверяет восемь TCP/UDP-listeners, завершает процесс через stdin-команду и проверяет закрытый JSONL. Локальные API `/api/v1/local-receiver/status`, `/start`, `/stop` возвращают только состояние и краткую сводку. Получатель пока слушает только loopback; он **не встроен в планировщик реальных прогонов и интерфейс**. Поле `routeVerified` всегда `false`, а `routeStatus` — `UNVERIFIED`: это не готовый локальный PROXY-тест. Сборка и синтаксис проверены, сетевой запуск не выполнялся.

## Что уже можно использовать

- `src/pb_net_endpoint.py` принимает TCP/UDP, связывает сообщение с `test_id`, `run_id`, `sequence`, `phase` и пишет JSONL с адресами, байтами и SHA-256 полезной нагрузки. По умолчанию он слушает loopback, но принимает явный bind IPv4/IPv6. Это база для локального получателя; сам по себе запуск процесса ещё не доказывает маршрут PROXY.
- `modules/VpsEvidence.psm1` и `modules/Assertions.psm1` уже сопоставляют клиент, событие получателя и маршрутные записи ProxyBridge. Для локального режима нужен источник свидетельств с теми же проверками идентичности и полноты, без зависимости от SSH.
- `src/pb_perf_client.c` сейчас допускает только `--offline` или `--self-test` и создаёт искусственные образцы с `non_product_acceptance=true`. Реального сетевого бенчмарка в этом файле пока нет. Восемь сценариев `scenarios/performance/performance.catalog.json` остаются `CAPABILITY_GATED`.
- Текущий `RunReadinessService` требует Linux ServerReady для любого реального задания. Проверку готовности необходимо определять по выбранному получателю; нельзя просто убрать её.

## Роли и топология

**Локальный вариант:** генератор, ProxyBridge и выбранный пользователем прокси работают на Windows-ПК; контролируемый получатель запускается TestLab на этом же ПК. **Удалённый вариант:** ProxyBridge остаётся на Windows, прокси удалён, контролируемый получатель работает на доступной удалённой машине, в том числе на управляемом Linux-узле. Местоположение прокси и местоположение получателя фиксируются раздельно. Любой вариант требует независимого события получения, иначе маршрутный результат остаётся неопределённым.

Контроллер владеет локальным получателем: выбирает свободные разрешённые порты, задаёт bind-адрес, создаёт отдельный run-owned журнал, наблюдает точный PID/путь процесса, проверяет все ожидаемые TCP/UDP-listeners, останавливает процесс и подтверждает освобождение портов и закрытие журнала. Пользователь не устанавливает сервер вручную. Локальный журнал читается только после закрытия окна наблюдения; старые строки и записи другой попытки исключаются.

### Главная проблема локального пути

По [документации ProxyBridge](https://interceptsuite.com/docs/proxybridge/configuration-windows/) трафик к `127.0.0.1`/`::1` обычно идёт напрямую. Поэтому запрос к локальному получателю через loopback может измерить скорость Windows loopback, даже если приложение настроено на PROXY. Привязка получателя к LAN-адресу той же машины тоже **не считается** доказательством перехвата без наблюдения фактического пути. Когда клиент и прокси на одном ПК, IP-адрес источника у получателя может быть одинаковым для DIRECT и PROXY.

Предлагаемый gate перед PROXY-бенчмарком:

1. Узнать фактический адрес назначения, правило ProxyBridge и выбранный proxy config; убедиться, что адрес достижим выбранному прокси.
2. Короткой контрольной серией DIRECT и PROXY проверить, что наблюдаемые пути различимы именно в этой конфигурации. Нужны независимые признаки: события локального получателя **и** подтверждение соединения проверяемого процесса с выбранным прокси, с процессом/временем/назначением/попыткой. Для стороннего прокси не предполагать наличие его логов. Способ наблюдения сокета на Windows или достоверного proxy-side события определить и проверить при реализации.
3. Если прямой и прокси-маршрут неразличимы, показать «Невозможно подтвердить путь через прокси» и не присваивать корректности `PASS`, даже при правильном ответе получателя. Результаты такого прогона не включать в подтверждённый A/B-бенчмарк ProxyBridge.
4. Для BLOCK полное отсутствие записи получателя допустимо только при завершённом окне сбора и положительном доказательстве активного BLOCK-правила; отсутствие ответа клиента само по себе недостаточно.

Известный дефект UDP source endpoint не является автоматическим запретом на измерение производительности (уточнение 2026-09-30). Предлагаемый benchmark может учитывать доставленные ответы от подтверждённого relay выбранного процесса ProxyBridge при совпадении run/sequence/payload; строгую проверку источника сохранять отдельно, с отрицательным вердиктом при фактически наблюдаемой подмене. Адрес/порт relay подтверждать для текущего прогона, не разрешать произвольные источники и не полагаться на константу 34011. Считать полезные доставленные байты/уникальные пакеты и RTT; потери, дубликаты, неверные payload и неожиданные источники оставлять в результатах. A/B выполняется с одним генератором и одинаковой политикой учёта, с пометкой об ограничении корректности, когда дефект наблюдался. Это измерение транспорта; совместимость приложений, требующих исходного endpoint, не доказана. DIRECT с обнаруженным неверным путём не является успешным baseline; отсутствие доказательств маршрута по-прежнему запрещает подтверждённое сравнение. Короткий opt-in режим реализован и выполнен 2026-09-30: 64 пакета, первые 8 исключены из метрик как прогрев. Пауза 100 мс после ответа; скорости относятся к этому заданному темпу. Клиент использует исходное назначение, relay определяется из live CLI и независимо проверяется Get-NetUDPEndpoint по принадлежащему CLI PID/пути. Источник классифицируется на ORIGINAL_ENDPOINT / OWNED_RELAY / UNEXPECTED, strict actual_result сохранён; unexpected/payload failure прекращает серию и делает performance INCONCLUSIVE. UDP RTT измерен QPC от send до recvfrom, до хеширования/JSON. Объёмы подтверждены каждым run/sequence/хешем получателя, сокетом и UDP ASSOCIATE; callback не используется как счётчик пакетов. Реальный receipt и краткий итог RU/EN: artifacts/local-route/socks5-udp-benchmark-1. Все 64 источника — OWNED_RELAY; исправление не наблюдалось. Ветка без подмен вычисляется из исходных источников/достаточных свидетельств, но на исправленной сборке ещё не проверена. Исторический переход версий и UI ещё не реализованы. Наблюдатель psutil 7.2.2/Windows: PID/start/path, system CPU/RAM и раздельные CLI/proxy/receiver/generator/sampler, 250 мс; интервалы через границу фаз исключены, CPU нормирован на logical CPUs. Private RAM mean/max — по выборкам. Низкий CPU ограничен дискретностью счётчиков; стоимость драйвера отдельно и энергопотребление в ваттах не измерены. Следующая подготовка — длительная/высокая нагрузка, эта короткая серия её не заменяет.

Источник UDP-ответа проверять постоянно, даже при разрешённом продолжении benchmark: исходный endpoint / подтверждённый relay / неожиданный источник. Счётчики и статус выводить по наблюдениям текущего прогона, а не списку «неисправных версий». Все валидные ответы от ожидаемого источника при достаточном завершённом наблюдении позволяют отметить «Не обнаружено в этом прогоне»; любая подмена, в том числе в смешанной серии, остаётся дефектом. Нулевое число ответов не подтверждает исправление. Переход относительно сопоставимого прошлого прогона показывать с указанием проверенного режима; строгий продуктовый сценарий сохранять после исправления.

Контрольная серия не должна подменять основной тест и не требует обязательного TestLab-owned прокси вместо пользовательского. Возможность надёжной атрибуции для произвольного стороннего локального прокси пока **не доказана**; это технический риск локального режима, который решает первый реализационный срез.

## Контракт свидетельств получателя

Минимум в приватной записи: `run_id`, `attempt_id`, `scenario_id`, `endpoint_id`, `process_identity`, `transport`, локальный и наблюдаемый удалённый адрес/порт, `sequence`, время по монотонным часам, байты, результат проверки содержимого и завершённость окна сбора. Клиент и ProxyBridge связываются с теми же run/attempt и фактическими адресами. Для скорости считать **подтверждённые получателем полезные байты** за его окно, а не только байты, которые генератор попытался отправить. Для отправки и загрузки фиксировать оба направления.

Ситуации, которые нельзя превращать в успешный результат: разрыв журнала, потерянный конец окна, повторный или чужой run/attempt, несовпадение payload, неверный порт/процесс, недостаточная атрибуция PROXY, неостановленный получатель. Обнаруженный прямой обход PROXY или доставка при BLOCK — ошибка продукта при достаточных свидетельствах. Недостаток самих свидетельств — «Недостаточно данных», а не ошибка продукта.

## Измерение нагрузки на ПК

Один sampler запускается контроллером до генератора и останавливается после его завершения. Каждая запись имеет `run_id`, `window_id`, монотонное время и точную идентичность наблюдаемых процессов. Окна: спокойный фон → прогрев → измерение → восстановление. Одинаковая частота дискретизации и границы окон обязательны для A/B. Пропущенные или слишком редкие отсчёты помечают ресурсную метрику неполной.

| Метрика | Первый выпуск | Пояснение пользователю |
|---|---|---|
| CPU ProxyBridge | Средняя и пиковая доля CPU за измерительное окно | Вклад пользовательских процессов ProxyBridge; не автоматически включает драйвер |
| Память ProxyBridge | Средняя и пиковая private memory, итог после восстановления | Рост памяти виден отдельно от фоновых колебаний |
| CPU/память генератора и локального получателя | Отдельные ряды | Их затраты не приписывать ProxyBridge |
| CPU/память всего ПК | Фон, средняя/пик во время теста, восстановление | «Нагрузка на ПК», без ложной атрибуции одному процессу |
| Сеть и ошибки | Подтверждённые байты/с, операции/с, ошибки | Показывать рядом с CPU/памятью для оценки цена/результат |

CPU процесса считать по **приращению процессорного времени за интервал** и нормировать на число логических процессоров для процента от всего ПК. Учитывать краткоживущие дочерние процессы и не склеивать PID после перезапуска: идентичность включает время старта и путь. Если драйвер или служба не дают отдельной достоверной метрики, не включать их расход в подпись «CPU ProxyBridge»; общесистемная нагрузка всё равно видна. Для сравнения A/B показывать изменение при одинаковой пропускной способности либо совместно показывать скорость и расход ресурсов, без вывода «экономнее» из одного процента CPU при разной выполненной работе.

Первый экран результата: **Корректность**, **Скорость**, **CPU ПК / ProxyBridge**, **Память ПК / ProxyBridge**, **Стабильность**. Например: «Загрузка 82 МБ/с, CPU ProxyBridge 14%, память 310 МБ». Детальные графики и служебные идентификаторы доступны отдельно. При фоновом пике, ограничении генератора, недоступном sampler или неполном журнале вывод о сравнении помечается как недостаточно надёжный.

## Порядок внедрения

1. Добавить понятие `receiver_location` и run-owned локальный получатель; сохранять базовую структуру JSONL, где это возможно. Проверить остановку и полноту сбора вручную на ограниченном локальном прогоне, когда такой запуск будет разрешён задачей.
2. Ввести топологическую готовность и короткую калибровку различимости DIRECT/PROXY. До её успеха локальный PROXY-кейс остаётся недоступным. Удалённый Linux-путь продолжает использовать своё доказательство источника.
3. Добавить Windows-sampler и простой двуязычный итог, затем реальный bounded TCP workload, который получает подтверждение байтов. `pb_perf_client` использовать для сетевых метрик только после его реальной реализации или взять подходящий готовый генератор с проверенным путём.
4. Добавить A/B, UDP и длительную нагрузку после подтверждения корректности маршрута и качества временных рядов.

Новые автотесты кода TestLab по умолчанию не писать. До разрешённого реального испытания статус остаётся «спроектировано», а не «работает».

## Прямой трафик и добавленная задержка — уточнение 2026-09-30

Пользователь требует видеть сравнение с прямым трафиком, особенно для игр. Планируются три режима: «Напрямую / Direct», «Через прокси / Explicit proxy», «Через ProxyBridge / Through ProxyBridge». Один контролируемый получатель и сопоставимый генератор/полезный трафик; без режима явного прокси нельзя выделить расходы ProxyBridge отдельно от всего выбранного пути. DIRECT-правило продукта не является baseline. Перед сериями без ProxyBridge подтвердить отсутствие перехвата; остановленная служба и отсутствие известных GUID не превращают неподтверждённый global cleanup в доказанный прямой путь. Не обходить действующие gates.

В кратком результате — RTT median/p95/p99 и разница в мс, вариация RTT с указанной формулой, потери, поздние ответы относительно выбранного порога, полезная скорость и CPU/RAM. Прямой ↔ ProxyBridge показывает суммарную разницу выбранного пути; явный тот же прокси ↔ ProxyBridge уточняет добавленную стоимость перенаправления с оговоркой о клиентском адаптере. RTT UDP echo отражает проверяемый путь; ICMP ping отдельно не доказывает UDP-перехват. Одностороннюю задержку из RTT/2 не считать измеренной. Параметры/прогрев/длительность/инструментирование одинаковы, повторения чередуются; фоновые изменения и известная подмена UDP остаются видимыми. Новых baseline/явный-прокси серий в этом обсуждении нет, GUI/код не менялись. Следующий шаг — подготовить и проверить сопоставимый прямой baseline до увеличения нагрузки.

Никаких автотестов кода.

## Прямой baseline и парные повторы — выполнены 2026-10-01

`-TrafficMode OFF -Protocol UDP -UdpBenchmark` добавляет режим `product-off-direct`: выбранный ProxyBridge не запускается. Для каждой серии проверяются SCM Stopped с ожидаемым файлом, отсутствие GUI/CLI, известных WFP-объектов и имён ProxyBridge/WinDivert среди загруженных драйверов. Ошибка перечисления или изменение состояния блокирует результат. Read-only PSAPI observer временно включает SeDebugPrivilege текущего elevated helper token и восстанавливает его. Отсутствие всех сторонних фильтров этим не доказано, global cleanup/version_switch_ready остаются false.

В OFF и UNRULED одинаковые native binary, ID нагрузки/размеры пакетов, controlled receiver, idle proxy worker и sampler; через idle proxy в OFF данные не идут. Для сопоставимых повторов из PowerShell администратора:

```powershell

  -UdpProxyPythonPath C:\Users\LabAdmin\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe `
```
