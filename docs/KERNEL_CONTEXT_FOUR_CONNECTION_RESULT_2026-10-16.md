## Что удалось связать

Core PID19008 (hex4a40), TID4636 (hex121c). Все четыре исходных query выполнены в одном потоке, seq1..4; их QPC интервалы не перекрываются. В KD ровно четыре соответствующих QUERY_READ→QUERY_STATUS пары с тем же PID/TID, ioctl980000dd и одинаковыми thread/scope/endpoint/record внутри каждой пары. Порядок пар соответствует порядку Core query. Native клиент PID11840 (hex2e40) совпал с PID CREATE_POST и возвращённым ctx_pid.

| Core seq | Core socket | Native peer port | Record alias | Core API / KD status |
| --- | ---: | ---: | --- | --- |
| 1 | 512 | 60585 | R1 | 0 / 0 |
| 2 | 524 | 60584 | R2 | 0 / 0 |
| 3 | 520 | 60582 | R3 | 0 / 0 |
| 4 | 548 | 60583 | R4 | 0 / 0 |

Для каждого R1..R4 в сохранённом порядке наблюдается:

`CREATE_POST → ACCEPT_RETRIEVE_RESULT(status0) → ACCEPT_JOIN(тот же record/endpoint) → QUERY_READ → QUERY_STATUS(status0) → FREE_ENTER → FREE_CALL_RETURN`.

У CREATE_POST assigned=record, refs1, size32. У paired retrieval/join совпали thread/scope/endpoint/NBL, previous=NULL. При FREE_ENTER refs0, прежние context pointer и size32; FREE_CALL_RETURN совпал по thread/scope и бывшему адресу record. В этих четырёх цепочках адреса record уникальны. Сам call return не доказывает всю работу allocator; освобождённый record не читался.

Привязка Core↔KD **порядковая в пределах одного PID/TID и полного присланного захвата**. Независимого Core seq/socket в строках KD и общей QPC шкалы нет. Нельзя переносить этот метод на многопоточный или усечённый capture без проверки неоднозначности. CREATE и accepted endpoint различаются; их связывает record, не равенство endpoint. Полного NBL association/parent transfer/arbitrary-write покрытия по-прежнему нет.

## Почему двадцать C0000225 не являются исходным отказом

Все двадцать относятся к ACCEPT_RETRIEVE_RESULT, не к QUERY_STATUS. Их output/previous=NULL, а endpoint ни разу не совпал с endpoint четырёх запросов Core. Пять записаны в контексте PID6608, пятнадцать — PID19008. Даже совпадение с PID Core не устанавливает владельца принимаемого endpoint или связь с исходным query.

Дисковый код и ранее проверенный live fragment показывают: после retrieve `test eax,eax` / `jne` уводит при ненулевом статусе к общему ACCEPT_JOIN, пропуская store record в endpoint. Есть также входы в join без retrieve. Это объясняет разницу событий в этом захвате; не объясняет, почему контекст отсутствует у конкретного исходно отказавшего соединения.

Core stdout содержит успешные исходные query, успешные четыре SOCKS5 upstream legs и Direct соединения других процессов. Рабочие потоки Core также встречаются в accept событиях без record. Что именно за каждый из этих двадцати endpoint, отдельно не установлено. Гипотеза обычного отсутствия redirect context у служебного/неперенаправленного соединения возможна, но endpoint не привязан к socket tuple. Поэтому критерий «любой ACCEPT_RETRIEVE_RESULT=C0000225 означает исследуемый сбой» неверен для этой диагностики. Нужна связь с конкретным отказавшим исходным query Core и native соединением.

Один и тот же адрес NBL встречается в разных событиях, включая успешные и NULL retrieval. Само повторение адреса не доказывает идентичность пакета или потерю контекста: повторное использование адреса не исключено.

## Текущий стоп-пункт

Согласованная одна four-only проба завершена, повторять её не нужно. В конце USER вывода все семь точек d, затем g; сейчас новых команд WinDbg нет.

Следующее разрешённое действие — офлайн-подготовка контролируемого воспроизведения исходного отказа. Предпочтительный порядок для будущего отдельного решения:

1. Сначала контроль с отключёнными точками на нынешних Windows binaries, прежних pinned CLI/Core/driver и original listener. Четыре соединения не подтверждают сохранение старого нагрузочного signature после смены Windows. Кандидат для планирования — прежняя последовательность4→64→256→640→4 (968 соединений); это ещё не допуск к запуску и не существующий подготовленный kit. Сначала проверить подходящий workload/пределы времени и подготовить новый комплект, не ослаблять four-only gates.
2. Исходным воспроизведением считать конкретный failed original Core query с Winsock10022 и соответствующим native отказом. Один NULL accept retrieval, отсутствие драйверной ошибки или успех CTS не заменяют эту связь. Сохранить raw Core/CTS и фактическую очистку независимо от исхода; если signature не вернулся, не объявлять его исправленным.
3. Только после такого контроля выбрать минимальный KD профиль и ограниченный повтор, чтобы увидеть судьбу record именно этого пути. Учесть436–907ms query intervals под KD, критерии остановки, неполноту семи sites и новые frozen runtime hashes. Не выбирать executing PID как owner filter без проверки. Переход к runtime остаётся отдельно согласуемым.

Нового нагрузочного комплекта пока нет, текущий four-only wrapper не принимать за его замену. Сокращение профиля не объявлять полным lifecycle покрытием. Не начинать уровни64/256/640 или recovery автоматически.

Новый runtime запуск/enable согласовывается отдельно по конкретному подготовленному плану. Агент не выполняет debugger/Run. Продукт/драйвер/build/install/BCD/гипервизор не менять, соседнюю рабочую копию разработки не трогать. Цель остаётся установлением механизма исходного сбоя, а не прохождением теста увеличением очереди.
