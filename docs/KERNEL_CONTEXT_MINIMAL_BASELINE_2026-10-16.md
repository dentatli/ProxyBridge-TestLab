## Что проверять после пробы

1. Логгер: нет debugger read/syntax ошибок и PBKDM_UNREADABLE, команды продолжают VM, инвентарь после пробы отключён. Нечитаемая память означает неполный capture, не объяснение отказа продукта.
2. Native/Core: ровно четыре query `[CTXDIAG]` и четыре timing `[CTXTIMING]`, четыре уникальных native соединения с endpoint/GUID, исходный listener, реальные итоги и очистка. Нативный reporter оставляет DEBUGGER_PENDING; любой отказ сохраняется как отказ, не заменяется PASS.
3. Для каждого Core query сопоставить relay PID и thread с KD QUERY_READ/QUERY_STATUS, один thread/scope/endpoint и однозначную пару с ioctl980000dd. По каждому thread проверить число и порядок query, исключить посторонние/пропущенные события. Общей QPC шкалы Core/KD нет: совпадение времён или только PID не считать доказательством. Неоднозначное соответствие — binding pending.
4. Для конкретной пары query проследить record и endpoint через CREATE_POST, успешный ACCEPT_RETRIEVE_RESULT и ACCEPT_JOIN, затем FREE_ENTER/FREE_CALL_RETURN. CREATE и accepted endpoint могут различаться; повторное использование адреса record после free не считать тем же lifecycle. ACCEPT_JOIN сам по себе не доказывает store, failed retrieval raw_output_slot не считать действительным record.

Семь sites не дают полного NBL association/parent transfer/allocator или arbitrary-write покрытия. Отсутствие события не доказывает, что операция не происходила вне наблюдаемых sites. Если четыре соединения прошли, это проверка работоспособности и границ наблюдения; механизм исходного отказа и переход к полной нагрузке всё ещё требуют отдельного решения.
